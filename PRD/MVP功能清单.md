> 基于 [flow_sequence_v2.puml](./flow_sequence_v2.puml) 全流程梳理  
> 优先级定义：P0 = 一期 MVP 必须上线 | P1 = 二期完善 | P2 = 三期优化  
> 门店侧所有功能统一由平板承接，不单独开发店员 App

---

## 需求背景

### 市场环境

印度是全球第二大智能手机市场，年出货量超过 1.5 亿台，二手设备交易市场规模庞大但高度分散。当前市场存在三个核心痛点：

1. **估价不透明**：二手设备定价依赖人工经验判断，买卖双方信息严重不对称，消费者缺乏信任感。门店回收时"一言堂"式报价导致用户流失率高，成交转化率低。
2. **质检标准缺失**：行业缺乏统一的设备检测标准，IMEI、电池健康度、屏幕触控、外观成色等关键指标无客观记录。回收后的设备质量参差不齐，二次销售退货率高。
3. **流通效率低下**：回收、质检、定价、上架、销售各环节割裂，门店回收到设备后缺乏统一的出货渠道。跨区域库存不互通，热门机型一机难求、冷门机型长期滞销并存。

### 业务机会

通过**标准化质检 + 算法定价 + 统一商城**三端联动，构建从回收到再售的闭环平台：

- **供给端**：门店平板一体机完成外观影像采集与硬件自动审计，数据上云后由定价引擎统一计算抵扣价，从根本上解决估价随意性问题。
- **流通端**：旧机统一入区域总仓库，运营团队集中审核影像资料，审核通过后自动上架。门店不持有库存，专注于回收服务。
- **销售端**：同一 C 端 App 承载个人购买与企业批量采购两种模式，仓库统一发货，实现"一处回收、全域可售"。

## 核心业务目标

### 一期 MVP 验证目标

| 维度 | 目标 | 衡量指标 |
|------|------|----------|
| **跑通闭环** | 一台旧机从门店回收到最终售出的完整链路 | 端到端流转时长 |
| **验证定价模型** | 自动估价被用户和门店双方接受 | 报价接受率 |
| **验证审核效率** | 运营团队基于影像资料完成质量把关 | 审核通过率 + 人均日审核量 |
| **验证支付链路** | Razorpay UPI 支付在 C 端和 B 端均可用 | 支付成功率 |
| **验证仓储发货** | 仓库端入库→拣货→扫码→出库流程跑通 | 出库准确率 + 出库时效 |

### 长期目标（P1/P2 阶段延续验证）

| 维度 | 目标 |
|------|------|
| **B2B 规模化** | 门店通过企业采购模块批量补货，平台成为门店的稳定货源渠道 |
| **同城优先匹配** | 用户优先购买同城仓库设备，缩短物流时效，提升体验 |
| **数据驱动定价** | 积累交易数据后持续优化定价引擎，实现按区域/机型动态调价 |
| **标准化扩张** | 质检标准和运营流程可复制至更多城市和门店，支撑规模化 |

## 模块一：平板质检工具（门店一体机）

| 优先级 | 功能 | 说明 |
|--------|------|------|
| **P0** | 外观影像采集 | 拍照 + 录视频，覆盖边框/屏幕/后盖 |
| **P0** | 硬件自动审计 | USB 连接读取 IMEI、电池健康度、屏幕触控、传感器等 |
| **P0** | 外观拒收 | 外观无法回收时店员拍照上传+选择拒收原因，会话终止，不进硬件检测 |
| **P0** | 发票信息采集 | 可选：拍摄发票照片+录入金额日期，定价引擎以min(发票价,市场价)为基准 |
| **P0** | 综合数据上传 | 外观影像 + 硬件数据 + 发票信息(如有)打包上传至云端 |
| **P0** | 质检报告展示 | 平板端展示报告摘要和抵扣报价 |
| **P0** | 核销状态同步（平板端） | 平板展示核销流程实时状态，核销操作在店老板App和用户App完成 |
| **P0** | 审核调整通知 | 运营调整成色/扣款后推送至平板，供店员复盘质检质量 |
| **P0** | 到店用户 OTP 验证与注册 | 手机号+OTP验证身份，SMS含H5短链，自动匹配预约/注册/创建会话 |
| P1 | 离线质检缓存 | 网络中断时本地暂存，恢复后自动补传 |
| P1 | 预约信息加载（OTP后自动匹配） | OTP验证通过后自动加载预约信息，无需店员额外操作 |
| P2 | 门店数据看板 | 门店回收量/成交额统计 |

```

  ├── 平板一体机（OTP验证→采集→审计→发票→上传→报告→核销状态→审核调整通知）

  ├── 库管端（入库→翻新质检→出库任务→扫码核销→打印面单）

  └── 门店数据看板
```

## 核心判断逻辑

P0 保证一条完整闭环跑通：

> **门店平板质检 → 用户App接受 → 店老板核销 → DB发往仓库 → 库管翻新质检 → 运营审核上架 → C端浏览下单支付 → 仓库发货**

门店侧所有功能集中于平板一体机，不再单独开发店员 App。B2B 放在 P1 是因为它依赖 B2C 的商城、支付、路由、出库能力全部就绪后才能叠加，属于"增量"而非"基础"。换购预约放在 P1 是因为 MVP 阶段用户直接到店即可走完流程，预约非阻塞项。
