# 质检双检测方案评审文档：自检 App（方案A） vs H5 免安装自检（方案B）

> **文档目的：** 供团队内部评审「用户旧机硬件检测」的实现载体选型
> **文档版本：** v1.0 | **日期：** 2026-09-01 | **作者：** 何子豪
> **评审结论待定项：** 见 §11 决策点清单
> **关联文档：** `模块PRD/01_平板质检工具_PRD.md`（v2.0 双App方案）、`方案/技术API调研清单.md`

## 1. 背景与问题定义

### 1.1 为什么"一块平板完成全部质检"不成立

门店质检的信息需求分为三类，其中核心识别信息被操作系统硬性封锁：

| 信息类型 | 具体项 | 技术现状 |
|---------|--------|---------|
| **外观信息** | 划痕/碎裂/变形/腐蚀 | ✅ 拍照 + AI 识别，店员设备可完成 |
| **硬件功能** | 触控/传感器/摄像头/音视频/按键 | ⚠️ 必须在**旧机本体上运行代码**才能测（黑盒无法从外部测一台手机的扬声器） |
| **设备身份** | IMEI/SN/电池健康度%/激活锁 | ❌ Android 10+/iOS 均封锁程序化读取；激活锁只能服务端反查 |

已废弃路线（2026-09-01 决策）：平板 USB OTG + ADB/libimobiledevice —— Android 需用户开开发者模式（引发戒心），iOS 无等价物，双端流程分裂。

### 1.2 因此问题收敛为

> **"在旧机本体上跑的检测代码，用什么载体交付给用户？"**

- **方案 A**：原生自检 App（现行 PRD v2.0 方案，TAB-P0-14）
- **方案 B**：H5 网页自检（零安装，点链接即测）

两方案的店员侧（宿主 App）与服务端通道**完全相同**，差异仅在用户旧机侧的载体。

## 2. 方案总览（三通道架构）

无论 A/B，整体架构均为三通道，`session_id` 是唯一汇聚点：

```
┌─────────────────────────────────────────────────────────────┐
│                      云端中台（通道3）                        │
│   session_id 汇聚 · OCR管线 · IMEI反查(激活锁/黑名单/EMI)     │
│   定价引擎 · 去重指纹 · 状态机                                │
└────────▲──────────────────────▲─────────────────────────────┘
         │                      │
   ┌─────┴──────┐        ┌──────┴────────────────────┐
   │ 通道1 店员侧 │        │ 通道2 用户旧机侧（差异点）  │
   │ 宿主质检App  │        │ A=自检App   B=H5自检页     │
   │ OTP/拍照10+1 │        │ 硬件功能测试/截图上传       │
   │ 发票/扫码兜底 │        │                             │
   └────────────┘        └─────────────────────────────┘
```

## 3. 端到端流程对比

### 3.1 方案 A 流程（现行 PRD v2.0 + 店员主导修订）

> **操作模式：店员主导**（与方案 B 对齐）。授权锚点同样在 OTP 短信 H5 短链落地页；同意后落地页直接引导自检 App 下载（链接自动携带 session_id，无需再扫二维码绑定）。

```
① 店员登录宿主App → ② 用户OTP验证（SMS含H5短链）
→ ②.5 用户打开H5短链 → 落地页展示质检内容+隐私声明
     → 用户点击「同意并开始质检」★ 操作授权在此完成（合规锚点）
     → 落地页自动引导自检App下载（携带session_id深链）
→ ③ 生成session_id
→ ④ 旧机【安装自检App】★摩擦点（授权后店员操作安装）
     Android：落地页→下载APK→授"允许安装未知应用"→安装（2-5分钟，需教学）
     iOS：落地页→跳App Store→下载（需已登录Apple ID）→安装
→ ⑤ 打开自检App → 深链自动绑定session（免扫码）
→ ⑥ 自检App跑9项硬件测试（自动）
→ ⑦ 引导截「设置→关于本机」「设置→电池」→导入App→端侧OCR（IMEI/SN/电池健康度）
→ ⑧ 结果上传云端 → 展示完成态 + 检测结果摘要
→ ⑨ 店员：外观采集10张+视频 → 拒收判断 → AI检测/人工点检
→ ⑩ 店员：盒标扫码兜底IMEI + 发票采集（可选）
→ ⑪ 综合上传 → 云端查激活锁/黑名单 → 定价出价
→ ⑫ 报告展示 → 用户接受/拒绝
```

**预估用户侧耗时：④-⑧ 约 5-8 分钟（含安装，店员操作、用户在场目视）**

### 3.2 方案 B 流程（H5 免安装）

> **操作模式：店员主导。** 自检全程由店员在用户旧机上操作（用户在场目视）。操作授权在 OTP 短信 H5 短链落地页由用户点击确认（同意质检 + 隐私声明），授权后旧机交店员执行检测，流程合规不依赖"用户亲手操作"。

```
① 店员登录宿主App → ② 用户OTP验证（SMS已含H5短链）
→ ②.5 用户在自己手机上打开H5短链 → 落地页展示质检内容+隐私声明
     → 用户点击「同意并开始质检」★ 操作授权在此完成（合规锚点）
→ ③ 生成session_id；用户旧机打开H5自检页（店员输短码/扫店员码携带session）
→ ④ 旧机【点击链接打开H5自检页】★零安装，此后旧机由店员操作
→ ⑤ H5自动运行能力探测 → 按机型实际支持度执行6-7项自动测试
→ ⑥ 引导截「设置→关于本机」「设置→电池」→相册选择器上传截图→云端OCR
→ ⑦ 结果上传云端 → H5展示终态页：「自检完成 ✓ + 检测结果摘要」
     宿主App监听session，结果落地自动亮起下一步（无需任何"交还"动作衔接）
→ ⑧ 店员：外观采集10张+视频 → 拒收判断 → AI检测/人工点检
→ ⑨ 店员：拍用户手机「*#06#」拨号屏OCR兜底IMEI + 盒标扫码 + 发票采集
→ ⑩ 综合上传 → 云端查激活锁/黑名单 → 定价出价
→ ⑪ 报告展示 → 用户接受/拒绝
```

**预估用户侧耗时：④-⑦ 约 2-4 分钟（店员操作，用户在场目视）**

### 3.3 流程逐步对照表

| 步骤 | 方案 A | 方案 B | 差异评价 |
|------|--------|--------|---------|
| 操作授权 | H5 短链落地页点击「同意并开始质检」→ 引导 App 下载（深链带 session） | H5 短链落地页点击「同意并开始质检」→ 直接进入自检 | **两案一致**：授权锚点均在落地页，合规留痕 |
| 操作模式 | 店员主导（授权后旧机交店员安装+检测） | 店员主导（授权后旧机交店员检测） | 两案一致 |
| OTP 验证 | 相同 | 相同（短链即自检入口，天然复用） | B 多合一 |
| 会话绑定 | App 深链自动绑定 session（免扫码） | 短信链接自动带 session / 扫码 | 均免扫码，等效 |
| 检测载体获取 | **安装 App（Android 侧载授权 / iOS App Store）** | **点链接即用** | **核心差异：A 的最大流失风险点** |
| 硬件功能测试 | 9 项全跑（原生 API） | 6-7 项自动测 + 能力探测降级 | A 覆盖多 2-3 项 |
| IMEI/SN | 端侧 OCR（ML Kit / Vision） | 云端 OCR（复用服务端管线） | 等效，B 需网络 |
| 电池健康度% | 截图 + 端侧 OCR | 截图上传 + 云端 OCR | 等效 |
| 按键/距离/光线传感器 | App 内测（音量键）/部分测 | 转店员宿主 App 人工点检 | A 优 |
| 结果上传 | 原生上传（断点续传） | H5 上传（弱网体验依赖门店网络） | A 优 |
| 弱网/离线 | App 本地缓存强 | PWA/Service Worker 可缓解但弱于原生 | A 优 |
| 用户心理 | "要卖的手机还要装个App"（戒心） | 浏览器跑完即走，不残留 | B 优，可作为门店话术卖点 |
| 版本更新 | OTA/商店审核周期 | 服务端发布即时生效 | B 优 |
| 双端一致性 | Android/iOS 两套代码，需双端 QA | 一套代码，浏览器层吸收差异 | B 优 |

## 4. 检测项能力矩阵（核心评审材料）

> 图例：✅ 自动可得且精确 ｜ ⚠️ 可得但降级（推断/估算/部分平台）｜ ❌ 该载体拿不到，走兜底通道

### 4.1 硬件功能检测项

| # | 检测项 | A. 自检 App | B. H5 自检 | B 的降级路径 |
|---|--------|------------|-----------|-------------|
| 1 | 品牌 & 型号 | ✅ `Build.MODEL` / `hw.machine` 精确型号代码 | ⚠️ UA + WebGL GPU 字符串 + 分辨率/DPR 推断；主流机型准确，冷门机型可能只到品牌级 | 推断失败 → 店员确认；「关于本机」截图 OCR 交叉验证 |
| 2 | 存储容量 | ✅ `StatFs`/`NSFileManager` 精确 | ⚠️ `navigator.storage.estimate()` 估算，取整到 64/128/256 档 | 定价按档位足够；「关于本机」截图 OCR 交叉验证 |
| 3 | 电量 % | ✅ 双平台精确 | ⚠️ 仅 Android Chrome（`getBattery`）；iOS Safari 不支持 | iOS → 店员目视口述录入 |
| 4 | 屏幕触控 | ✅ 多点触控网格（MotionEvent/touchesBegan） | ✅ touch 事件多点网格，等效 | — |
| 5 | 屏幕显示/坏点 | ✅ 纯色轮播 | ✅ 纯色轮播，等效 | — |
| 6 | 加速度计/陀螺仪 | ✅ SensorManager/CoreMotion | ✅ DeviceMotion（iOS 13+ 需一次授权弹窗） | 用户拒绝授权 → 跳过标记"未测" |
| 7 | 距离/光线传感器 | ✅ 可测 | ❌ 无 Web API | 转店员宿主 App 人工点检（2 项小项） |
| 8 | 摄像头前/后 | ✅ Camera2/AVFoundation 实拍 | ✅ getUserMedia 前后摄预览+截帧 | — |
| 9 | 扬声器 & 麦克风 | ✅ 播放+回采 | ✅ WebAudio 播放+回采（iOS 需麦克风授权） | 拒绝授权 → 转店员人工 |
| 10 | 按键（音量/电源） | ⚠️ 音量键可捕获；电源键锁屏只能引导跳过 | ❌ 按键事件不进网页 | 转店员宿主 App 人工点检 |
| 11 | 振动马达 | ⚠️ Android 可测；iOS 无公开 API | ⚠️ Android `navigator.vibrate`；iOS 不支持 | 未测标记，非扣款项 |

### 4.2 设备身份项（双方案均无法直读，兜底通道相同）

| # | 项目 | A. 自检 App | B. H5 自检 | 共同兜底链 |
|---|------|------------|-----------|-----------|
| 12 | IMEI / SN | ❌ 无公开 API → 引导截图 + 端侧 OCR | ❌ 同 → 截图上传 + 云端 OCR | ①「关于本机」/`*#06#` 截图 OCR ② 店员拍旧机拨号屏 OCR（B 特有增强） ③ 盒标扫码 ④ 手工录入（15 位 Luhn 校验） |
| 13 | 电池健康度 % | ❌ → 「设置→电池」截图 + 端侧 OCR | ❌ 同 → 截图上传 + 云端 OCR | 不可得 → 标记"无法检测"，按中档扣款 |
| 14 | iOS 激活锁 / Android FRP | ❌ 设备端读不到 | ❌ 同 | 服务端拿 IMEI 查 iCloud / GSMA（见技术API调研清单 §1.2） |
| 15 | IMEI 黑名单 / EMI 分期锁 | ❌ | ❌ | 服务端查询（见技术API调研清单 §1.1/§1.3） |

### 4.3 去重指纹（服务端复合指纹的分量来源）

| 分量 | A. 自检 App | B. H5 自检 | 影响 |
|------|------------|-----------|------|
| IMEI/SN（主键） | OCR 获取 | OCR 获取 | 相同 |
| ANDROID_ID / idFV | ✅ 可读 | ❌ 网页拿不到 | B 缺失 |
| WebGL/Canvas 指纹 | 可选 | ⚠️ 可用但稳定性弱 | B 的替代分量 |
| 品牌型号+存储+电池 | 精确 | 推断/估算 | B 分量置信度略低 |

> **风险场景：** 无发票 + IMEI OCR 失败时需降级复合指纹去重 —— 此场景下 B 的指纹强度弱于 A。若 IMEI OCR 成功率 ≥ 90%，该风险影响可控（此为关键预研数据，见 §9）。

## 5. 能力探测与降级路由框架（方案 B 的配套要求）

方案 B 必须内置「能力探测 → 降级路由」框架，保证**双端用户看到同一条进度条**，差异封装在后台：

```
每项检测声明:
{
  item: "camera_front",
  capability_check: () => !!navigator.mediaDevices?.getUserMedia,
  primary:   async () => { /* H5 自动测试 */ },
  fallbacks: [
    { type: "upload_ocr",  desc: "截图上传云端OCR" },   // IMEI/电池健康度
    { type: "clerk_photo", desc: "店员拍屏OCR" },        // *#06# 屏
    { type: "clerk_manual",desc: "店员人工点检" },       // 按键/传感器
    { type: "skip_mark",   desc: "标记未测" }            // 振动等非扣款项
  ]
}

结果统一契约（A/B 共用，下游定价引擎不感知来源）:
{
  item: "camera_front",
  status: "normal | abnormal | timeout | manual_entry | not_tested",
  value: {...},
  source: "web | native | ocr | photo_ocr | manual | server",
  evidence: [文件引用...],
  confidence: 0.0-1.0
}
```

**流程一致性的保证机制：**
1. `session_id` 唯一汇聚（与现行 PRD 架构同构，不翻架子）
2. 统一数据契约，定价/去重/审计只消费字段不关心来源，**下游零改动**
3. 每项检测的能力探测在 H5 加载后 3 秒内完成，自动生成该机型的执行计划
4. UI 层双端同一条「N/9 步」进度条，个别项采集方式不同但不影响步骤数

## 6. 优劣势总览

### 6.1 方案 A（自检 App）

| 维度 | 评价 | 说明 |
|------|:---:|------|
| 检测覆盖 | ★★★★★ | 9 项全覆盖 + 精确指纹分量（ANDROID_ID/idFV） |
| 数据精确度 | ★★★★★ | 型号代码、精确存储容量 |
| 用户摩擦 | ★★☆☆☆ | **安装环节是第一流失点**：Android 侧载授权教学成本高；iOS 需 Apple ID 登录 |
| 用户心理 | ★★☆☆☆ | 旧机即将出售还要装 App，易引发数据安全戒心 |
| 双端一致性 | ★★★☆☆ | Android/iOS 两套原生代码，行为差异需双端 QA |
| 开发/维护成本 | ★★☆☆☆ | 双端原生开发 + APK 下载服务器 + 热点直传 + App Store 审核/版本周期 |
| 弱网/离线 | ★★★★★ | 原生本地缓存，断点续传 |
| 迭代速度 | ★★☆☆☆ | 商店审核周期不可控（iOS 尤甚） |

### 6.2 方案 B（H5 自检）

| 维度 | 评价 | 说明 |
|------|:---:|------|
| 检测覆盖 | ★★★☆☆ | 6 项等效 + 1 项降级可用 + 按键/距离/光线转人工；指纹分量弱 |
| 数据精确度 | ★★★★☆ | 型号推断（主流机型准确）、存储估算到档位 |
| 用户摩擦 | ★★★★★ | **零安装零注册，点链接即测**；入口复用 OTP 短信短链 |
| 用户心理 | ★★★★★ | 浏览器跑完即走不残留，可作门店话术："不安装任何软件" |
| 双端一致性 | ★★★★★ | 一套代码，浏览器层吸收平台差异 |
| 开发/维护成本 | ★★★★☆ | 单 H5 前端（可并入现有 H5 会话跟踪页体系）+ 复用云端 OCR 管线；约为 A 的 40-60% 工作量 |
| 弱网/离线 | ★★★☆☆ | 依赖门店网络；PWA/Service Worker 可缓存检测逻辑，但上传仍需网络 |
| 迭代速度 | ★★★★★ | 服务端发布即时生效 |

### 6.3 一句话对比

> **A 用 2-3 个小项 + 指纹强度的优势，换来了整个安装环节的流失风险和双端原生成本；B 覆盖检测主体，代价是 3 个小项转人工和指纹降级。**

## 7. 成本与工作量对比（估算）

| 项目 | 方案 A | 方案 B |
|------|--------|--------|
| 用户侧载体开发 | Android（Kotlin）+ iOS（Swift）双端原生，含端侧 OCR（ML Kit/Vision）、断点续传、本地加密缓存 | 单 H5 应用（React/Vue），含能力探测框架、截图上传 |
| 分发基础设施 | APK 下载服务器 + 二维码深链 + 蓝牙/热点直传 + App Store/Play 商店账号与审核 | 无（URL 即入口，复用现有短链服务） |
| 服务端增量 | session 绑定 API、结果接收 | 同左 + 云端 OCR 调用（管线复用外观 OCR） |
| QA 成本 | 双端机型矩阵测试 + 安装流程测试（各品牌侧载路径不同） | 浏览器兼容矩阵测试（Chrome/Samsung Internet/iOS Safari + 低端机型） |
| 相对工作量 | 100% | 约 40-60% |

## 8. 风险清单

| 风险 | 方案 | 等级 | 缓解措施 |
|------|:---:|:---:|---------|
| 安装流失（侧载授权卡住 / iOS 无 Apple ID） | A | **高** | 店员培训 + 图文引导；仍不可消除 |

## 10. 决策建议

**推荐：方案 B（H5 免安装自检）为主，方案 A 降级为 P1 增强路径（混合方案 C）。**

理由：
1. 安装摩擦是可预见的最大流失点，与"到店转化"核心指标直接冲突；B 的入口（OTP 短链）在现行 PRD 中天然存在，零额外成本
2. 9 项硬检中 B 覆盖 6 项等效 + 1 项降级可用；转人工的仅按键 + 2 个小传感器（均非核心扣款项）
3. 开发量约为 A 的一半，且一套代码天然保证双端流程一致
4. A 作为 P1 增强：当出现"指纹去重不足的高风险会话"或"深度诊断需求"时，再引导安装自检 App 做补充采集
5. **前置条件：§9 预研项 1、2 通过后再最终拍板**；若 H5 兼容性实测不达标，回退方案 A
