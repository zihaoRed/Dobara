# 质检单列表优化方案

> 结合「6 条优化点建议」与「重新质检 / 修改质检」的数据存储、流程交互，给出质检工具「质检记录单列表」的完整优化设计。
> 落点：01 PRD `TAB-P1-06 质检数据列表` + store-tablet `recordStore`/`InspectionRecordList`/`sessionProgress` + 需求池 `P3-P1-06`。

---

## 一、优化目标

把「散装卡片 + 6 态筛选」改成「按状态 Tab 分组的作业视图」，让店员一眼知道「今天有哪些活、每单能干什么、干到哪一步了」。

---

## 二、状态模型（5 个 Tab）

| Tab | 状态 | 定义 | 数据来源 |
|---|---|---|---|
| **待质检** | `pending` | 用户已预约、未开始质检 | 预约单（`appointment_pending`） |
| **质检中** | `inspecting` | 已开始质检、提交报价前 | 进行中的会话 |
| **质检完成** | `completed` | 已提交报价、进入核销 | 已提交的质检单 |
| **质检拒收** | `rejected` | 准入/外观拒收 | 拒收单 |
| **取消质检** | `cancelled` | 用户/店员取消 | 取消单 |

**两个「折叠」决策：**
- **上传失败**：不单独成 Tab，并入「质检中」，卡片上给「重新上传」按钮（对应 TAB-P0-03 断点续传）。
- **已核销**：不单独成 Tab，并入「质检完成」，用「交接进度」子状态表达（见下）。

---

## 三、各 Tab 内容与操作

### 3.1 待质检
- **展示**：预约单数据 —— 用户姓名/手机、设备品牌型号、**预约时间**（日期 + 时段）。
- **操作**：`开始质检`（顾客 OTP 二次核身后进入质检）、`取消质检`（二次确认后入「取消质检」）。
- **边界**：walk-in（无预约）用户走 OTP 后**直接进「质检中」**，不经过「待质检」。

### 3.2 质检中
- **展示**：进行中数据 —— 当前步骤、设备摘要、已采集进度（如「硬件完成 / 拍照 5/10」）。
- **操作**：`继续质检`、`修改质检`、`重新质检`、`取消质检`、`重新上传`（仅上传失败时）。

### 3.3 质检完成
- **展示**：提交报价后的质检单 + **交接进度**（子状态，卡片内展示）：
  - `待店老板录入` → `待用户确认核销` → `已核销`
  - （术语沿用 PRD 核销流程，不用「核验」）
- **操作**：`查看详情`（只读，跳报告/核销状态页）。

### 3.4 质检拒收
- **展示**：拒收单数据 + **拒收原因**（预设原因 + 照片缩略）。
- **操作**：`查看详情`（只读）。

### 3.5 取消质检
- **展示**：已取消数据 + 取消时间/取消方（用户取消 / 店员取消）。
- **操作**：无（或 `重新预约`入口，P1）。

### 3.6 卡片交互（优化点 6）
- **卡片不再展示「待质检/质检中/质检完成」等状态标签**（Tab 已表意）。
- 仅「质检完成」Tab 内保留「交接进度」子徽章（这是卡片需要单看的增量信息）。

## 四、重新质检 / 修改质检设计

### 4.1 语义

| 操作 | 语义 | 触发场景 |
|---|---|---|
| **重新质检** | 放弃本次全部数据，**从头再来** | 扫错设备/串单、报价过期需重出、店员想重来 |
| **修改质检** | 保留已采集数据，**只改某一步/某几项** | 外观点检选错、硬件某项误判、重拍某张照片、补拍发票 |

### 4.2 数据存储

现有数据按 sessionId 分片存 sessionStorage（`dobara_hardware_<sid>`、`dobara_inspect_<sid>`、`dobara_condition_<sid>`、`dobara_device_color_<sid>`、`dobara_appointments_<sid>`）+ 单条进度 `dobara_tablet_session_progress`。

**重新质检 —— 归档 + 新会话（推荐）**
- 原 sessionId 全部分片**打包归档**，记录上标记 `status='voided'` + `voidedAt` + `voidedReason`，保留审计。
- 生成**新 sessionId**，进度 `completedIndex=-1`、`currentStep='session'`。
- 若已提交报价，旧报价**作废**（C 端对应订单变「报价已过期/已作废」）。

**修改质检 —— 保留 + 覆盖 + 下游失效**
- 数据**保留**，只覆盖被修改那一步的分片。
- 进度 `completedIndex` **回退**到被修改步骤。
- 被修改步骤之后的**下游分片标记失效**（见 4.4）。

### 4.3 流程交互

**重新质检**
```
质检中卡片 → 点「重新质检」
  → 二次确认（"将放弃本次质检数据并重新开始？"）
  → 归档原会话 → 生成新会话 → 进入第一步（decision/OTP）
```

**修改质检**
```
质检中卡片 → 点「修改质检」
  → 进入流程，步骤导航解锁（已完成步骤可回跳）
  → 跳回某步修改 → 覆盖该步数据
  → 下游失效数据清除 → 从该步继续往后走
```

### 4.4 下游依赖失效链（修改质检的关键）

步骤顺序：`decision → admission → hardware → photo/video → inspect → condition → invoice → submit → report`

| 修改的步骤 | 需作废/重算的下游 |
|---|---|
| admission | 硬件、拍照/视频、外观AI、点检、定价 |
| hardware（品牌型号） | **颜色（AI自动关联）**、定价 |
| photo/video | 外观AI、定价 |
| inspect（外观扣款） | 定价 |
| condition（维修/配件/功能扣款） | 定价 |
| invoice | 定价 |

关键：**颜色**依赖 hardware 型号、**定价**依赖 inspect/condition/invoice 扣款。

### 4.5 MVP 边界（定稿）

1. **修改质检**：MVP 仅支持**提交报价前（质检中）**修改，且**只回退到最近一步**（「返回上一步重做」）。提交报价后（质检完成态）**不允许修改，只能重新质检**。
2. 下游失效：MVP 先做**「回退一步 → 该步及之后全部清除」**（简单不出错），「任意步修改」的细粒度失效链留到后续。
3. **重新质检**：允许从「质检中」「质检拒收」「取消质检」发起。

## 五、数据模型补充字段

`IInspectionRecord` 需新增：

| 字段 | 用途 |
|---|---|
| `appointmentTime` / `appointmentDate`+`appointmentSlot` | 待质检展示预约时间 |
| `rejectionReason` | 质检拒收展示原因 |
| `handoverStatus` | 质检完成交接进度：`pending_owner` / `pending_user` / `verified` |
| `cancelledAt` / `cancelReason` / `cancelledBy` | 取消质检 |
| `voidedAt` / `voidedReason` | 重新质检归档 |

`TInspectionRecordStatus` 调整：`pending` / `inspecting` / `completed` / `rejected` / `cancelled`（去 `redeemed`、`upload_failed`，二者折叠进 `completed` 的 `handoverStatus` 与 `inspecting` 的「重新上传」）。

## 六、状态流转图

```
                 ┌────────── 取消质检 ──────────┐
                 ↓                              │
[待质检 pending] ──开始质检(OTP)──→ [质检中 inspecting]
    │ 取消质检                        │ 继续/修改/重新上传
    ↓                                 ├── 重新质检 → (归档) 新会话 → 质检中
[取消质检 cancelled]                  ├── 取消质检 → 取消质检
                                      ├── 拒收 → [质检拒收 rejected]
                                      └── 提交报价 → [质检完成 completed]
                                                          │ 交接进度:
                                                          │ pending_owner → pending_user → verified(已核销)

[质检拒收 rejected] ──重新质检──→ (归档) 新会话 → 质检中
```

## 八、已确认决策（定稿）

1. ✅ **已核销**：并入「质检完成」（用「交接进度」子状态 `verified` 表达）。
2. ✅ **上传失败**：并入「质检中」（卡片上「重新上传」按钮）。
3. ✅ **修改质检边界**：仅提交报价前 + 仅回退最近一步。
4. ✅ **质检拒收重新质检**：开放（从「质检拒收」可发起重新质检，归档原单 → 新会话）。
