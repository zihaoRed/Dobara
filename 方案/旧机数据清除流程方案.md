# 旧机数据清除流程方案

> 目标：用户接受报价后，旧机归平台所有，但旧机仍存有用户个人数据（照片/通讯录/账号/支付信息等）。在设备离店、入库、翻新、再上架前，必须**彻底清除用户数据**，防止隐私泄露与激活锁（Activation Lock/FRP）导致设备无法翻新再售。

---

## 一、背景与目标

- **背景**：回收换购的旧机在交割给平台后，若未清除个人数据就进入仓库/再售，会泄露下一位用户能接触到的原主人隐私（合规风险：印度 DPDP Act / GDPR 同类要求）。
- **目标**：定义一套「报价接受后、设备离店前」在门店完成的**标准化数据清除流程**，保证设备：
  1. 无个人数据残留（已抹除/恢复出厂）；
  2. 无激活锁 / FRP 锁（已退出账号、关闭查找）；
  3. 可安全进入仓库 → 翻新 → 再售。

---

## 二、触发时机与流程位置

**触发**：用户接受报价（`quote accept`）后立即触发「数据清除任务」。

**位置**：在**门店内**、设备**发往仓库前**完成（用户需在场配合退出账号）。

**推荐时序**（与当前核销三段式衔接）：

```
用户接受报价
  → 【数据清除】店员引导用户清除旧机（退出账号 + 关闭查找 + 抹除/恢复出厂）
      └── 清除验证通过
  → 店老板扫码录入新机 IMEI + 录入售价实付（可并行，见下）
  → 用户核对 IMEI 尾号 + 确认核销（核销摘要附带「旧机已清除」标识）
  → 发仓库（清除完成是发仓库的硬性前置条件）
```

> 说明：「数据清除」（店员 + 用户操作旧机）与「店老板录入新机信息」（店老板操作）可**并行**，互不阻塞；但**「发仓库」必须等待清除验证通过**。

---

## 三、清除内容（按平台分）

### iOS 设备

| 步骤 | 操作 | 位置 |
|------|------|------|
| 1 | 退出 Apple ID / iCloud（需输入密码，同时关闭「查找我的 iPhone」） | 设置 → Apple ID → 退出登录 |
| 2 | 移除屏幕锁（Face ID / Touch ID / 密码） | 设置 → 面容/触控 ID 与密码 |
| 3 | 移除 SIM 卡 / SD 卡 / eSIM | 物理 + 设置 |
| 4 | 抹掉所有内容和设置 | 设置 → 通用 → 传输或还原 → 抹掉所有内容和设置 |
| 5 | 验证：重启后进入「你好」初始界面，**无激活锁提示** | 目视 |

### Android 设备

| 步骤 | 操作 | 位置 |
|------|------|------|
| 1 | 退出 Google 账号（移除账号） | 设置 → 账户 → 移除账号 |
| 2 | 移除屏幕锁（PIN / 图案 / 指纹） | 设置 → 安全 |
| 3 | 移除 SIM 卡 / SD 卡 / eSIM | 物理 + 设置 |
| 4 | 恢复出厂设置（抹掉所有数据） | 设置 → 系统 → 重置 → 抹掉所有数据 |
| 5 | 验证：重启后进入初始设置向导，**无 FRP 锁（Google 账号验证）提示** | 目视 |

---

## 四、操作分工与原则

| 角色 | 职责 |
|------|------|
| **用户（旧机主人）** | 退出自己的账号（需密码）、关闭查找、移除屏幕锁、确认抹除/恢复出厂 |
| **店员（CLK）** | 引导操作、目视验证清除结果、在质检工具记录「清除完成 + 验证通过」 |

**核心原则**：退出账号 / 关闭激活锁**必须由用户本人操作**（涉及账号密码），店员不得代操作——避免纠纷，也符合「账号归属用户」的合规边界。店员只负责**引导 + 验证 + 记录**。

---

## 五、标准清除流程（店员操作指引）

1. 报价接受后，质检工具自动进入「数据清除」环节（或列表内点「开始清除」）。
2. 店员当面引导用户按平台清单逐项操作（退出账号 → 关闭查找 → 移除 SIM/SD → 抹除/恢复出厂）。
3. 店员目视确认：设备重启后进入初始设置界面，**无激活锁/FRP 提示**。
4. 店员在质检工具勾选「清除完成」+「验证通过」，提交；系统记录时间戳与店员 ID。
5. 状态变更为「已清除」，进入后续核销/发仓库。

---

## 六、验证标准与证据留痕

| 项 | 标准 |
|----|------|
| iOS 验证通过 | 重启后出现「你好 Hello」界面，可进入设置向导，无「此 iPhone 已关联 Apple ID」激活锁 |
| Android 验证通过 | 重启后出现初始设置向导，无「请输入之前同步的 Google 账号」FRP 提示 |
| 证据 | 记录 `device_wipe`：session_id、wipe_status、account_signed_out、find_my_off、factory_reset_done、verified_by_clerk、verified_at、clerk_id、failure_reason |

---

## 七、异常与失败处理

| 场景 | 处理 |
|------|------|
| 用户忘记 Apple ID / Google 密码，无法退出激活锁 | 暂缓发仓库，设备暂存门店；引导用户通过官网找回密码/关闭激活锁；约定时间内完成则继续，否则标记「清除失败」走特殊处理（拒收或折价回收） |
| 设备无法开机 | 已在准入检查 ADM-04（无法开机）拒收，不进入本流程 |
| 报失/被盗设备（激活锁无法关闭） | 已在准入检查 ADM-05（报失）拒收，不进入本流程 |
| 清除中断（断电等） | 重新执行清除流程，不影响已完成的账号退出 |
| 清除失败 | 状态标记 `wipe_failed`，设备**不得发仓库/上架**；进入门店滞留处理 |

## 八、状态机与数据模型

### 新增清除子状态（挂在回收会话/设备上）

```
[待清除 pending_wipe] → [清除中 wiping] → [已清除 wiped]（验证通过，终态）
                                      └── [清除失败 wipe_failed]（异常态）
```

- **已清除 `wiped`** 是「发仓库」（`pending_inbound`）的**硬性前置条件**：未清除 → 禁止生成发货单。

### 新增数据模型 `device_wipe`

```json
{
  "session_id": "UUID",
  "device_id": "UUID",
  "wipe_status": "pending_wipe | wiping | wiped | wipe_failed",
  "account_signed_out": true,
  "find_my_off": true,
  "factory_reset_done": true,
  "verified_by_clerk": true,
  "clerk_id": "UUID",
  "verified_at": "ISO8601",
  "failure_reason": "string | null"
}
```

## 九、涉及端与 PRD 落点

| 端 | 落点 | 改动 |
|----|------|------|
| 质检工具 | 01 PRD | 新增「数据清除」步骤（店员引导清单 + 勾选记录 + 验证通过） |
| 服务端 | 06 PRD | 状态机新增 `pending_wipe/wiping/wiped/wipe_failed`；`device_wipe` 模型；发仓库前置校验（未清除禁止生成 store_shipment） |
| C 端 | 02 PRD | 核销确认摘要可附带「旧机已清除」标识（可选，P1） |
| 内部业务 | 05 PRD | 库管入库确认时校验「已清除」状态（可选，P1） |

---

## 十、待确认的决策点

1. **时序**：清除放在「核销确认之前」（推荐，清除是核销/发仓库的前置）还是「核销确认之后、发仓库之前」？
2. **清除失败的处理口径**：暂缓 + 用户找回密码后继续（推荐），还是直接拒收/折价回收？
3. **是否需要 C 端可见**：用户在核销摘要里是否要看到「旧机已清除」确认项？（影响 C 端是否改动）
4. **优先级**：建议 P0（数据安全是合规红线，且是发仓库硬前置）。

> 定下这 4 点后，我可将其正式拆分为 PRD 需求（质检工具/服务端）并同步 UI 与需求池。
