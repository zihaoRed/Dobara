## CLOUD-P0-08 运营审核
**优先级：** P0
**功能描述：**
运营人员在 Web 后台对待上架设备进行审核。审核时对比质检影像与系统判定的成色等级及扣款项是否一致。若一致则直接上架；若不一致，运营人员直接在审核界面调整成色等级或扣款项（如降级外观、增加扣款），系统重新计算回收价和商城售价后上架。不设"拒绝上架"操作——所有设备均会上架，只是价格可能因调整而变化。
**审核流程：**
```
待上架设备进入任务队列
  → 运营人员打开审核工作台
    → 查看设备外观影像（10 张照片 + 1 段视频）+ 硬件检测摘要 + 当前成色等级 + 扣款明细
    → 判断机况是否与系统判定一致
      ├── 机况一致 → 点击"直接上架"
      │     → 上传商品主图（必填）
      │     → 设备状态 → [在库可售]
      │
      └── 机况不符 → 点击"调整后上架"展开调整面板
            → 下调成色等级 / 补勾扣款项
            → 填写调整原因（必填）
            → 系统重新计算回收价 + 商城售价
            → 上传商品主图（必填）
            → 推送调整详情至对应门店平板
            → 设备状态 → [在库可售]

```
**审核界面要素：**
| 区域 | 内容 |
|------|------|
| 任务队列 | 按入库时间排序的待审核设备列表，支持按品牌/机型/成色等级筛选 |
| 审核工作台-左侧 | 10 张外观照片可切换查看 + 视频播放器（支持暂停/拖动/全屏） |
| 审核工作台-右侧 | 硬件检测摘要（电池/屏幕/传感器/存储/摄像头/扬声器/按键）+ 当前成色等级 + 扣款明细（逐项列出） |
| 商品主图上传 | 运营从系统图片库选择或本地上传一张新机精修图作为商城商品列表主图（与质检原始照片区分），支持预览裁剪 |
| 操作区 | "直接上架"按钮（机况一致）+ "调整后上架"按钮（机况不符，展开调整面板） |
**运营调整面板（点击"调整后上架"时展开）：**
| 可调整项 | 说明 |
|----------|------|
| 成色等级 | 可下调（如 B→C、B→D），不可上调（防止虚标高等级卖高价） |
| 外观扣款项 | 可新增/修改店员未勾选的扣款项（如店员遗漏了屏幕划痕，运营可补勾 A2 扣款项） |
| 硬件扣款项 | 可新增店员漏判的硬件扣款（如店员未标记触控异常，运营从检测结果中确认后补勾） |
| 调整原因 | 必填，文本输入框，简要说明为何调整（如"屏幕划痕在视频中清晰可见，店员未勾选"），最少 10 字 |
**调整后系统自动执行：**
| 动作 | 说明 |
|------|------|
| 重新计算回收价 | 基于调整后的成色等级和新增扣款项，重新跑定价引擎（CLOUD-P0-01） |
| 重新计算商城售价 | 基于新的回收价和成色等级，重新计算挂牌售价 |
| 推送调整详情至平板 | 通知门店：调整了哪些项、原价格 → 调整后价格、调整原因（参见 TAB-P0-06） |
| 设备状态 → [在库可售] | 直接上架至商城，不阻塞流转 |
**业务规则：**
| 规则项 | 说明 |
|--------|------|
| 无拒绝操作 | 所有设备均上架，不存在"拒绝上架"按钮；极端劣质设备可通过降级+多扣款压低价格后上架 |
| 成色不可上调 | 运营仅可下调成色等级（如 B→C），不可上调（如 C→B）；上调操作被系统禁用 |
| 调整原因必填 | 任何时候选择"调整后上架"，调整原因为必填字段，不少于 10 个字符 |
| 商品主图必填 | 无论直接上架还是调整后上架，运营必须上传至少一张商品主图，未上传不可提交上架 |
| 调整可叠加 | 运营可在同一审核会话中同时下调成色等级和补勾多项扣款 |
| 不可回退 | 上架操作一旦提交不可撤回，设备立即进入在库可售状态 |
| 审核时效 | 设备入库后超过 24 小时未审核，系统在任务队列中标记"超时待审"橙色提醒 |
| 调整日志 | 所有调整操作记录操作人、时间、调整前后对比、调整原因，用于门店复盘和运营绩效考核 |
**验收标准：**
- [ ] 任务队列按入库时间倒序排列，超 24 小时未审标记橙色
- [ ] 任务队列支持按品牌/机型/成色等级筛选，筛选结果实时更新
- [ ] 审核工作台同时展示外观影像（10 张照片可点击切换 + 视频可播放/暂停/全屏）、硬件检测摘要、当前系统判定的成色等级、逐项扣款明细
- [ ] 商品主图支持本地上传（JPG/PNG，最小 800x800px）和从系统图片库选择，上传后可预览和裁剪
- [ ] 机况与系统判定一致时，运营点击"直接上架"→ 上传商品主图 → 确认提交 → 设备上架
- [ ] 机况不符时，运营点击"调整后上架"展开调整面板：可下调成色等级（不可上调）、可补勾/新增扣款项、必须填写调整原因（≥10 字）
- [ ] 调整后系统自动重新计算回收价和商城售价，审核界面实时预览新价格
- [ ] 调整详情（调整项 / 原价 / 新价 / 原因）实时推送至对应门店平板（TAB-P0-06）
- [ ] 所有操作（直接上架/调整后上架）均需上传商品主图，未上传不可提交
- [ ] 上架操作一旦提交不可撤回
- [ ] 每台上架设备记录审核人、审核时间、审核结果（通过/调整）、操作日志

## CLOUD-P0-11 平台角色与权限管理
**优先级：** P0
**功能描述：**
平台系统管理员通过运营后台管理全平台的组织架构（门店/仓库）、用户角色与权限。系统采用 RBAC 权限模型，以 7 个预置角色和 22 个原子权限编码为基础，实现精细化的功能访问控制和门店/仓库级数据隔离。所有账号创建、角色分配、权限变更操作均需由系统管理员执行。同一账号可拥有多个角色（每个角色绑定不同的门店/仓库），登录后可在 App/Web 内切换角色视图。

### 编码体系
| 实体 | 格式 | 示例 |
|------|------|------|
| 门店 | `ST-{州码2位}-{4位序号}` | `ST-MH-0001` |
| 仓库 | `WH-{州码2位}-{4位序号}` | `WH-MH-0001` |
| 平板设备 | `TAB-{门店编码}-{2位序号}` | `TAB-ST-MH-0001-01` |
| 店员 | `STAFF-{门店编码}-{3位序号}` | `STAFF-ST-MH-0001-001` |

印度各邦双字母代码：MH(马哈拉施特拉), DL(德里), KA(卡纳塔克), TN(泰米尔纳德), GJ(古吉拉特), UP(北方邦), WB(西孟加拉), RJ(拉贾斯坦)

### 角色管理功能
| 功能 | 说明 |
|------|------|
| 新建自定义角色 | 输入角色名称、描述，勾选该角色可访问的权限编码集合；不可与系统预置角色重名 |

### 门店/仓库管理
**创建门店：**
```
SA 登录运营后台 → "组织管理" → "新建门店"
  → 填写门店信息：
      ├── 门店名称（如 "Dobara - Mumbai Andheri"）
      ├── 所属州/城市（下拉选择，州决定编码前缀）
      ├── 详细地址
      ├── 门店联系电话（公开给C端用户，需验证格式）
      ├── 营业时间（可选）
      ├── GPS 坐标（可选，用于C端同城推荐和门店导航）
      └── 备注
  → 系统自动生成门店编码（如 ST-MH-0001，按州+序号自增）
  → 保存 → 门店状态 = "active"
```
**创建仓库：**
```
SA → "组织管理" → "新建仓库"
  → 填写仓库信息：
      ├── 仓库名称（如 "Mumbai Central Warehouse"）
      ├── 所属州/城市
      ├── 详细地址（用于退货收件地址）
      ├── 联系电话
      ├── 服务门店（多选，关联哪些门店）
      └── 备注
  → 系统自动生成仓库编码（如 WH-MH-0001）
```
**门店/仓库列表功能：**
| 功能 | 说明 |
|------|------|
| 搜索筛选 | 按名称、编码、州、状态筛选 |
| 查看详情 | 门店/仓库完整信息 + 关联账号数 + 当前设备数 |
| 编辑门店 | 修改名称、地址、电话、营业时间等 |
| 门店关店 | 状态 active → closed；触发关联账号批量禁用 + 平板远程锁定（详见门店App PRD 账号生命周期） |
| 门店重开 | 状态 closed → active；需手动恢复账号 |
### 账号管理功能
**创建账号（三步流程）：**
```
SA 在运营后台 → "账号管理" → "创建账号"

Step 1: 基本信息
  ├── 输入手机号（10 位印度手机号，登录凭证，全局唯一）
  ├── 输入姓名
  ├── 设置初始密码（或勾选"系统自动生成"→ 8位随机含大小写+数字）
  └── 选择账号类型：内部员工 / 店老板

Step 2: 角色分配
  ├── 选择一个或多个角色
  │     ├── ROLE-OWN → 需进一步选择绑定门店
  │     ├── ROLE-CLK → 需进一步选择绑定门店
  │     ├── ROLE-WH → 需进一步选择绑定仓库
  │     ├── ROLE-DB → 不需绑定组织（跨门店）
  │     ├── ROLE-OPS → 不需绑定组织
  │     └── ROLE-ENT → 不需绑定组织
  └── 每个角色可设置"有效期限"（可选，用于临时工/短期授权）

Step 3: 确认创建
  ├── 预览：手机号、姓名、角色列表、绑定组织、初始密码
  ├── 点击"确认创建"
  └── 系统自动：
        ├── 创建 user 记录（account_status = "pending_activation"）
        ├── 插入 user_role_assignment 记录（每条角色一条记录）
        ├── 若 ROLE-CLK/ROLE-OWN → 自动生成店员编号（STAFF-{门店编码}-{序号}）
        └── 发送邀请 SMS（含临时密码 + App 下载链接 + 门店名称）
```
**邀请 SMS 模板：**
```
[Platform] You've been added as [角色名] at [门店/仓库名].
Login: your phone number
Temp Password: XXXXXXXX
Download: [App Store / Play Store 短链]
Change your password after first login.
---
आपको [门店名] में [角色名] के रूप में जोड़ा गया है।
लॉगिन: आपका फ़ोन नंबर | पासवर्ड: XXXXXXXX
ऐप: [短链] | पहले लॉगिन के बाद पासवर्ड बदलें।
```
**账号列表与操作：**
| 功能 | 说明 |
|------|------|
| 创建账号 | 三步流程（基本信息 → 角色分配 → 确认创建），系统自动发送邀请 SMS |
| 编辑账号 | 修改姓名、角色分配、门店/仓库绑定、启用/禁用状态 |
| 禁用账号 | 禁用后该账号即时无法登录，5 分钟内当前会话自动登出，历史数据保留 |
| 重新启用 | 状态 disabled → active，原角色和权限不变 |
| 账号列表 | 按端/角色/门店/仓库/状态筛选，展示：用户ID、姓名、手机号(脱敏)、角色、绑定组织、状态标签、最近登录时间 |
| 重置密码 | 生成新临时密码 → 发送 SMS → 用户下次登录需重新激活（设新密码+同意协议） |
| 更换手机号 | 输入新手机号 → OTP 验证 → 更新 phone → 新旧手机号同时收到通知 SMS |
| 强制踢出 | 该账号所有设备的 JWT 立即失效（加入黑名单），正在使用的会话强制登出 |
| 查看详情 | 完整账号信息 + 角色分配历史 + 登录历史 + 操作审计 |
**账号状态标签：**
| 状态 | 标签颜色 | 说明 |
|------|:---:|------|
| `pending_activation` | 橙色 | 待激活（收到邀请但未登录），7 天后自动清理 |
| `active` | 绿色 | 正常使用中 |
| `locked` | 红色 | 密码错误 5 次临时锁定（15 分钟） |
| `disabled` | 灰色 | 管理员已禁用 |
| `removed` | 灰色 | 已被移除（不可逆，终态） |
| `deleted` | 灰色 | 用户已注销（终态） |
### 多角色切换
| 场景 | 说明 |
|------|------|
| 同一账号多角色 | 如某员工同时持有 ROLE-OWN + ROLE-DB，登录后切换角色视图 |
| 切换行为 | 切换角色后生成新 JWT（含目标角色的权限声明），刷新界面 |
| 权限计算 | 每个角色独立 JWT；当前 token 的 permissions = 该角色的权限集合 |
| 真实案例 | 一家门店的老板可能也是该区域多家门店的 DB——OWN(ST-MH-0001)+DB(null) |
### 门店/仓库数据隔离
| 规则项 | 说明 |
|--------|------|
| 门店隔离 | ROLE-OWN 和 ROLE-CLK 通过 JWT 中的 org_id=ST-MH-0001 实现数据隔离，只能访问本门店数据 |
| 仓库隔离 | ROLE-WH 通过 JWT 中的 org_id=WH-MH-0001 实现数据隔离，只能操作本仓库 |
| DB 跨门店 | ROLE-DB 的 org_id=NULL，可跨门店查看结算和营收数据，但无写权限 |
| 跨门店授权 | 区域经理等特殊情况可创建自定义角色，授予多门店/多仓库的 inspection:read 权限 |
| 数据范围变更 | SA 修改账号的 org_id 绑定后，用户下次切换角色或重新登录时生效 |
| 平板绑定 | 平板设备绑定唯一门店；店员登录时校验 store_id(平板) == store_id(店员)，不匹配则拒绝 |
### 业务规则
| 规则项 | 说明 |
|--------|------|
| 权限粒度 | 按 22 个原子权限编码控制；自定义角色可任意组合权限编码 |
| 权限变更生效 | 角色权限修改后，持有该角色的在线用户需刷新 JWT（2 小时内自动刷新） |
| 默认角色 | 系统预置 7 个角色（SA/OPS/OWN/CLK/WH/DB/ENT），不可删除，可修改权限配置 |
| 管理员保护 | ROLE-SA 由系统初始化脚本创建，不可被其他管理员禁用或删除 |
| 店员上限 | 默认每个门店最多 10 个 ROLE-CLK 店员，运营后台可配置 |
| 邀请过期 | 创建账号后 7 天内未激活 → 自动清理（user 和 user_role_assignment 记录删除） |
| 操作日志 | 所有门店/仓库创建、角色创建/修改、账号创建/禁用/权限变更操作记录审计日志 |

## CLOUD-P0-13 运营配置中心
**优先级：** P0
**功能描述：**
运营后台集中管理平台所有可动态调整的业务参数、选项列表和规则阈值。配置中心将每个可调项暴露为可视化表单控件（开关/数字输入/下拉/列表编辑），变更后即时生效或按规则生效，无需发版或重启服务。所有配置变更记录操作日志。配置中心按业务域分为 7 个配置组，SA 和具有 `pricing:config` 权限的 OPS 角色可操作。

**设计原则：**
| 原则 | 说明 |
|------|------|
| 零代码变更 | 所有可调参数均通过后台 UI 修改，不通过代码常量或配置文件 |
| 即时生效 | 修改保存后推送到 Redis，服务端实时读取最新值；部分参数（如JWT时长）需下一次签发时生效 |
| 变更审计 | 每次修改记录：操作人、时间、配置项key、旧值→新值、变更原因（可选） |
| 版本回滚 | 每项配置保留最近 10 次历史值，支持一键回滚到任意历史版本 |
| 默认值保护 | 所有配置项有系统默认值；运营修改过的项标记"已自定义"；支持恢复默认 |
| 全局 vs 门店级 | 大部分参数为全局配置；标注"门店级"的可按门店独立设置（如店员上限） |

### 配置项通用功能
**配置列表页：**
| 功能 | 说明 |
|------|------|
| 按配置组筛选 | 7 个配置组 Tab 切换（A-G） |
| 搜索 | 按 key 或说明文字模糊搜索 |
| 状态标签 | 默认值(灰) / 已自定义(蓝) / 门店覆盖(橙) |
| 快速跳转 | 侧边锚点导航，点击跳转到对应配置组 |
**配置编辑：**
| 控件类型 | 适用场景 | 交互 |
|------|------|------|
| 开关 | 布尔型配置 | 点击即生效 |
| 数字输入 + 单位 | 金额/时长/百分比 | 输入后失焦保存，校验上下限 |
| 下拉选择 | 有限的枚举值 | 点击选择即生效 |
| 列表编辑器 | 选项列表（如颜色、拒收原因） | 拖拽排序 + 增删改 + 每个选项含 key/label/label_hi 三个字段 |
**变更历史与回滚：**
```
点击配置项 → 展开"变更历史"
  → 展示最近 10 次变更记录：
      时间 | 操作人 | 旧值 | 新值 | 变更原因（如有）
  → 每条历史记录右侧有"回滚到此版本"按钮
  → 点击 → 二次确认 → 立即生效
```
**业务规则：**
| 规则项 | 说明 |
|------|------|
| 权限分级 | 配置组 A/B/C/D/G → `pricing:config` 权限可操作；配置组 E/F → 仅 `admin:role_mgmt`(SA) 可操作 |
| 即时生效 | 保存后通过 Redis Pub/Sub 通知所有服务节点刷新配置缓存 |
| 类型校验 | 数字型配置有 min/max 校验；文本型有长度校验；选项型校验 key 唯一性 |
| 依赖校验 | 关联配置联动校验（如免运费阈值 ≥ 标准配送费） |
| 操作日志 | 每次修改记录操作人、时间、key、旧值、新值、变更原因（可选） |

- [ ] 安全参数修改后即时生效
- [ ] 门店级配置可覆盖全局默认值，门店列表展示自定义标记
- [ ] 每项配置保留最近 10 次变更历史
- [ ] 支持一键回滚到任意历史版本
- [ ] 数字型配置有 min/max 范围校验
