## 1. 模块概述
## 1.1 模块定位
云端中台服务端是 Dobara 平台的**核心业务逻辑中枢**，负责从定价计算、核销确认、库存管理、支付集成到订单路由、国际化等全链路的服务端业务处理。所有前端客户端（平板质检工具、C 端 App、门店综合 App（含店老板/库管/DB 三角色）、运营后台）均通过本模块的 RESTful API 进行数据交互。
## 1.2 技术边界

| 边界项 | 说明 |
|--------|------|
| 服务框架 | 待定（推荐 Node.js / Go / Java Spring Boot） |
| 数据库 | PostgreSQL (主库) + Redis (缓存/锁/会话) |
| 消息队列 | RabbitMQ / Kafka (异步任务：路由分发、通知推送、审计日志) |
| 对象存储 | AWS S3 / MinIO (影像文件、语言资源包) |
| 支付网关 | Razorpay (UPI Intent / 原路退款) |
| 短信网关 | Twilio / MSG91 / WhatsApp Business API |
| 部署架构 | 微服务或模块化单体，水平可扩展 |
## 1.3 通用设计原则

| 原则 | 说明 |
|------|------|
| 幂等性 | 所有写操作支持幂等键 (idempotency_key)，防止重复提交 |
| 审计日志 | 所有关键操作写入不可篡改的 append-only 审计日志表 |
| 敏感数据加密 | IMEI、手机号等 PII 在数据库中以 AES-256-GCM 加密存储，日志中脱敏 |
| API 版本控制 | URL 路径携带版本号：`/api/v1/...` |
| 错误码统一 | 所有 API 返回统一的 `{code, message, data}` 响应结构，错误码集中管理 |
| Accept-Language | 所有 API 支持通过请求头 `Accept-Language` 返回 en/hi 对应语言的错误消息 |

## 2. P0 功能详细设计

## 2.1 CLOUD-P0-01 定价引擎
**优先级：** P0
**功能描述：**
接收平板上传的硬件检测数据和店员外观点检结果，通过"基础定价-折旧扣款矩阵"计算旧机最终抵扣价，并自动判定设备成色等级。同时为商城侧自动计算挂牌售价。运营管理员可通过可视化配置面板调整各项扣减参数。
**定价引擎总流程：**

```
质检数据上传
  │
  ├── 3.3.2.0 准入检查
  │     ├── 命中拦截 → [拒绝回收]（终态）
  │     └── 通过 → 继续
  │
  ├── 3.3.2.1 基准价确定 + 折旧扣款计算
  │     ├── 确定基准价（发票/市场）
  │     ├── 累加硬件检测扣款
  │     ├── 累加外观功能扣款
  │     └── 累加配件缺失扣款
  │
  ├── 3.3.2.2 成色等级判定（逐级熔断）
  │     └── 输出 A / B / C / D
  │
  ├── 3.3.2.3 价格计算与风控
  │     ├── Floor Price 保底约束
  │     ├── 30 分钟有效期
  │     └── 输出最终回收价 + 扣款明细
  │
  └── 3.3.2.4 商城售价计算
        ├── 基准加价率 × 回收价
        ├── 市场参考价上下限约束
        └── 输出商城挂牌售价

```

## 3.3.2.0 准入检查（定价前置拦截）
在进入定价流程之前，系统先执行准入检查。命中以下任一条件的设备直接标记为"拒绝回收"，不进入定价计算，不创建 IMEI 库存记录。
**拦截规则表：**

| 编号 | 拦截项 | 判断依据 | 数据来源 | 处理方式 | 用户提示 |
|------|--------|----------|----------|----------|----------|
| ADM-01 | IMEI 黑名单 | 与本地/第三方黑名单库比对（报失/被盗/运营商锁） | 平板读取 + 服务端查询 | 拒绝回收 | "该设备无法回收" |
| ADM-02 | iCloud/FRP 未退 | 平板硬件检测读取激活锁状态 | 平板硬件检测 | 拒绝回收 | "请退出账号后再回收" |
| ADM-03 | 进水/受潮 | LCI 进水指示器触发，或主板有明显腐蚀痕迹 | 平板硬件检测 + 店员目视 | 拒绝回收 | "设备存在进水痕迹，无法回收" |
| ADM-04 | 设备无法开机 | 平板检测不到设备响应 | 平板硬件检测 | 拒绝回收或走"配件回收"通道 (P2) | "设备无法开机" |
| ADM-05 | 设备被报失/被盗 | 与 DoT CEIR 或第三方黑名单库比对 IMEI | 服务端查询外部 API | 拒绝回收 | "该设备已被报失，无法回收" |
| ADM-06 | 设备仍在分期/EMI 中 | 查询 NBFC 贷款状态 API 或用户自行申报 | 服务端查询外部 API / 用户申报 | 拒绝回收 | "设备仍在分期付款中，请结清贷款后再回收" |
| ADM-07 | 设备被网络/运营商锁定 | IMEI 查询运营商锁状态 | 服务端查询外部 API | 拒绝回收 | "设备已被运营商锁定，请先解锁" |
**准入检查数据模型：**
```json
{
  "admission_id": "UUID",
  "session_id": "UUID",
  "imei": "string (encrypted)",
  "check_results": [
    {
      "check_type": "blacklist",
      "status": "pass|fail",
      "detail": "string",
      "checked_at": "ISO8601"
    }
  ],
  "overall_status": "pass|rejected",
  "rejection_reason": "string | null",
  "created_at": "ISO8601"
}

```
**业务规则：**

| 规则项 | 说明 |
|--------|------|
| 执行顺序 | 准入检查为定价引擎的**同步前置**步骤，任一命中则立即终止，不执行后续定价逻辑 |
| 第三方 API 容错 | IMEI 黑名单/CEIR/NBFC 等第三方 API 调用超时（> 5s）时，标记为"未验证"并放行，但记录告警日志；此降级策略仅用于避免阻塞门店业务，P2 阶段改为同步必需 |
| 运营后台可查看 | 被拒绝回收的设备信息在运营后台可查看，用于监控和分析拒绝原因分布 |
| 不可逆转 | 准入拒绝不可逆转，同一 IMET 不可重新提交 |
**验收标准：**
- [ ] ADM-01 ~ ADM-07 全部拦截项生效，命中后设备不进入定价
- [ ] 第三方 API 超时 5s 后降级为"未验证"并放行，记录告警
- [ ] 被拒绝记录的设备信息在运营后台可查询
- [ ] 准入检查耗时 < 2 秒（不包含外部 API 调用时间）

## 3.3.2.1 基础定价与折旧扣款矩阵 (Depreciation Deduction Matrix)
**定价总公式：**

```
基准价 (Base Price) = {
    min(发票价格, 市场基准价)    // 用户提供了发票
    市场基准价                    // 用户未提供发票
}
最终回收价 (Trade-In Price) = 基准价 + 存储溢价 - SUM(硬件检测扣款) - SUM(外观·功能扣款) - SUM(维修历史扣款) - SUM(配件缺失扣款)
最终回收价 = max(最终回收价, Floor Price)    // 受保底价约束

```

##### 3.3.2.1.1 基准价来源

| 价格来源 | 说明 | 配置方式 |
|----------|------|----------|
| 市场基准回收价 | 运营后台按【品牌 → 型号 → 最低存储版本】维护，以 INR 为单位 | 运营后台手动维护，P2 接入第三方价格数据自动刷新 |
| 区域调价因子 | 同一型号不同区域的基准价可独立配置（P1 阶段实现） | 运营后台按区域配置调价系数 |
| 发票价格封顶 | 若用户在质检时提供了购买发票，基准价 = min(发票价格, 市场基准价) | 自动计算 |
**发票价格封顶机制详解：**

```
if (invoice_provided) {
    base_price = min(invoice_price, market_base_price);
} else {
    base_price = market_base_price;
}

```
- 发票价作为基准价的**上限**，防止在市场短期涨价时以高于用户购买价的价格回收
- 发票价**不可抬价**：若发票价格高于市场基准价，仍取市场基准价
- 示例 1：iPhone 14 Pro 市场基准价 INR 62,000，用户发票价格 INR 55,000，基准价取 INR 55,000
- 示例 2：同上机型，用户发票价格 INR 80,000，基准价取 INR 62,000（发票不抬价）
- 审计要求：发票价格、基准价计算结果均写入定价审计日志

##### 3.3.2.1.2 存储容量溢价

| 规则项 | 说明 |
|--------|------|
| 基准参照 | 以该型号最低存储版本（如 64GB）对应的市场基准价为计算起点 |
| 溢价方式 | 每升高一档存储（64GB→128GB, 128GB→256GB, 256GB→512GB, 512GB→1TB），按固定溢价表加价 |
| 溢价表维护 | 运营后台按品牌维护各存储档位的溢价金额（INR 整数） |
| 示例 | iPhone 12 64GB 基准价 INR 14,000，128GB 溢价 INR 2,000，256GB 溢价 INR 4,000。若检测为 256GB，基准价 = 14,000 + 4,000 = INR 18,000 |
**存储溢价配置表结构：**
```json
{
  "brand": "Apple",
  "model": "iPhone 12",
  "base_storage": 64,
  "storage_premium_tiers": [
    {"storage_gb": 128, "premium_inr": 2000},
    {"storage_gb": 256, "premium_inr": 4000},
    {"storage_gb": 512, "premium_inr": 6000}
  ]
}

```

##### 3.3.2.1.3 扣款维度一：硬件自动化检测扣款
硬指标，由平板检测工具客观读取，店员不可修改。所有扣减金额在运营后台可配置。
**电池健康度 (Battery Health, BH)：**

| 编号 | 触发条件 | 扣减金额（配置项） | 附加动作 |
|------|----------|-------------------|----------|
| HW-BH-01 | 90% <= BH < 100% | 不扣减 | 无 |
| HW-BH-02 | 85% <= BH < 90% | 扣减 X1 (默认 INR 500) | 无 |
| HW-BH-03 | 80% <= BH < 85% | 扣减 X2 (默认 INR 1,200) | 无 |
| HW-BH-04 | 70% <= BH < 80% | 扣减 X3 (默认 INR 2,500) | 平板提示"建议更换电池" |
| HW-BH-05 | BH < 70% | 扣减 X4 (默认 INR 4,000) | 平板强制提示"电池需更换"，计入维修历史 |
**非原厂部件检测：**

| 编号 | 扣款项 | 触发条件 | 扣减金额（配置项） | 标记 |
|------|--------|----------|-------------------|------|
| HW-SCR-01 | 屏幕非原厂 | 屏幕芯片编码不匹配 | 扣减 Y1 (默认 INR 3,000) | "屏幕已更换" |
| HW-CAM-01 | 后置摄像头非原厂 | 摄像头模块编码不匹配 | 扣减 Y2 (默认 INR 1,500) | "摄像头已更换" |
| HW-MB-01 | 主板有维修痕迹 | 检测到主板焊接/飞线/屏蔽罩缺失 | 扣减 Y3 (默认 INR 5,000) | "主板有维修" |
| HW-BIO-01 | Face ID / Touch ID 不可用 | 生物识别模块不可用 | 扣减 Y4 (默认 INR 2,000) | "生物识别异常" |
| HW-TCH-01 | 触控异常 | 屏幕触控测试存在死区/断触 | 扣减 Y5 (默认 INR 2,500) | "屏幕触控异常" |

## 3.3.2.2 成色等级判定规则 (Condition Rating Rules)
系统根据硬件检测结果与外观勾选情况，自动判定设备成色等级。判定采用**"从高到低逐级熔断"** (Cascading Fuse Logic) 机制：从最高等级 (A / 99 新) 开始逐一匹配条件，任一项不满足则熔断下沉至下一等级，一旦落入某等级即不可回升，最终锁定的等级即为设备成色。

```
判定起点：A 级（99 新）
  │
  ├── A 级条件全满足？──── YES ──→ 等级 = A
  │         │ NO（熔断）
  │         ▼
  ├── B 级条件全满足？──── YES ──→ 等级 = B
  │         │ NO（熔断）
  │         ▼
  ├── C 级条件全满足？──── YES ──→ 等级 = C
  │         │ NO（熔断）
  │         ▼
  └── 自动落入 D 级 ─────────────→ 等级 = D

```
**各等级判定规则表：**

| 等级 | 名称 | 判定规则（以下条件须**同时满足**） |
|------|------|-----------------------------------|
| **A** | 99 新（几近全新） | (1) 电池 >= 90% **AND** (2) 全原厂配件（HW-SCR-01/HW-CAM-01/HW-MB-01 均未触发） **AND** (3) 屏幕无任何划痕（CO-SCR-01~06 均未勾选） **AND** (4) 边框无任何磕碰（CO-BDY-01~04 均未勾选） **AND** (5) 显示完美（CO-SCR-04/05/06 均未勾选） **AND** (6) 所有功能正常（CO-FNC-01~08 均未勾选） **AND** (7) 配件齐全（CO-ACC-01~03 均未勾选） **AND** (8) 无维修历史（CO-RPR-01~04 均未勾选） |
| **B** | 95 新（轻微使用痕迹） | (1) 电池 >= 85% **AND** (2) 屏幕/主板/摄像头为原厂（HW-SCR-01/HW-MB-01/HW-CAM-01 均未触发） **AND** (3) 屏幕仅允许无划痕或轻微划痕（CO-SCR-01 可勾选，CO-SCR-02~06 不可勾选） **AND** (4) 边框仅允许轻微掉漆（CO-BDY-01 可勾选，且 < 2 处；CO-BDY-02~04 不可勾选） **AND** (5) 显示正常（CO-SCR-04/05/06 均未勾选） **AND** (6) 所有功能正常（CO-FNC-01~08 均未勾选） |
| **C** | 90 新（明显使用痕迹） | (1) 电池 >= 80% **AND** (2) 屏幕和主板必须原厂（HW-SCR-01/HW-MB-01 均未触发），允许非核心维修（HW-CAM-01 和 CO-RPR-01~04 可触发） **AND** (3) 屏幕允许肉眼可见划痕（CO-SCR-01/02 可勾选，CO-SCR-03/05/06 不可勾选） **AND** (4) 边框允许明显磕碰（CO-BDY-01/02 可勾选，CO-BDY-03/04 不可勾选） **AND** (5) 显示允许轻微老化（CO-SCR-04 可勾选，CO-SCR-05/06 不可勾选） **AND** (6) 功能性问题 <= 1 项（CO-FNC-01~08 中 <= 1 项被勾选） |
| **D** | 85 新（大量瑕疵） | 满足以下任一即落入：(1) 电池 < 80% **OR** (2) 屏幕/主板有更换记录（HW-SCR-01 或 HW-MB-01 触发） **OR** (3) 屏幕碎裂或显示异常（CO-SCR-03/05/06 任一勾选） **OR** (4) 边框变形或后盖碎裂（CO-BDY-03/04 任一勾选） **OR** (5) 功能性问题 >= 2 项 |
**熔断示例：**

| 示例 | 设备状况 | 熔断路径 | 最终等级 | 说明 |
|------|----------|----------|----------|------|
| #1 | 外观完美，全原厂，但电池 78% | A→B→C→**D** | D | 电池 < 80% 直接触发 D 级 |
| #2 | 电池 92%，全原厂，外观无瑕，但 Face ID 不可用 | A→B→**C** | C | Face ID 不可用触发功能性问题 <= 1 项，B 级要求所有功能正常故熔断 |
| #3 | 电池 88%，屏幕有轻微划痕 (CO-SCR-01)，边框轻微掉漆 (CO-BDY-01)，全原厂，全部功能正常 | A→**B** | B | 轻微划痕 + 轻微掉漆在 B 级容忍范围 |
| #4 | 电池 95%，屏幕明显划痕 (CO-SCR-02)，其余完美 | A→B→**C** | C | B 级不允许 CO-SCR-02 明显划痕 |
| #5 | 电池 82%，Face ID 不可用，闪光灯异常 | A→B→C→**D** | D | 功能性问题 2 项触发 D 级 |
**验收标准：**
- [ ] 熔断逻辑正确：从 A 级开始逐级匹配，一旦不满足当前级条件则下沉，不可回升
- [ ] 全部 4 个等级判定条件覆盖所有扣款项
- [ ] 边缘 case 测试：电池 90.0% 应算 90% 以上（A 级容许可），89.9% 应算 < 90%
- [ ] 相同机况设备产生相同等级（一致性）
- [ ] 等级判定耗时 < 100ms

## 3.3.2.3 价格计算与风控逻辑
##### 3.3.2.3.1 多重扣款累加规则
各项硬件扣款与外观扣款之间为**累加关系**，互不替代。

```
总扣款 = SUM(所有触发的硬件检测扣款) +
         SUM(所有被勾选的外观扣款) +
         SUM(所有被勾选的功能缺陷扣款) +
         SUM(所有被勾选的维修历史扣款) +
         (维修项 >= 3 ? Rpenalty : 0) +
         SUM(所有被勾选的配件缺失扣款)

```
**累加示例：**

| 示例 | 触发的扣款 | 扣款明细 | 总扣款 |
|------|-----------|----------|--------|
| #1 | 电池 65% + 屏幕非原厂 + 后盖碎裂 | X4 (4,000) + Y1 (3,000) + B4 (3,000) | INR 10,000 |
| #2 | 电池 82% + 屏幕轻微划痕 + 缺少充电器 | X2 (1,200) + A1 (300) + P1 (500) | INR 2,000 |
| #3 | 电池 72% + 屏幕碎裂 + Face ID 不可用 + 扬声器异常 + 充电口异常 | X3 (2,500) + A3 (3,500) + Y4 (2,000) + F5 (800) + F2 (1,000) | INR 9,800 |
##### 3.3.2.3.2 保底价 (Floor Price) 防御机制

| 规则项 | 说明 |
|--------|------|
| 配置方式 | 运营后台为每个【品牌 → 型号 → 最低存储版本】配置最低保底价（INR 整数） |
| 判定逻辑 | `final_trade_in_price = max(calculated_price, floor_price)` |
| 作用 | 无论累计扣款金额多大，最终回收价不得低于保底价，防止极端扣款叠加导致回收价过低 |
| 审计 | 当 Floor Price 生效时（即计算价 < 保底价），在审计日志中记录差值 |
**Floor Price 示例：**

| 场景 | 基准价 | 累计扣款 | 理论价 | Floor Price | 最终回收价 | 是否触发保底 |
|------|--------|----------|--------|-------------|-----------|-------------|
| iPhone X 64GB | INR 12,000 | INR 11,500 | INR 500 | INR 3,000 | **INR 3,000** | 是 |
| iPhone 12 128GB | INR 22,000 | INR 8,000 | INR 14,000 | INR 5,000 | **INR 14,000** | 否 |
| Samsung S21 128GB | INR 15,000 | INR 14,800 | INR 200 | INR 4,000 | **INR 4,000** | 是 |
##### 3.3.2.3.3 定级与定价分离

| 设计原则 | 说明 |
|----------|------|
| 等级只看状况 | 成色等级反映的是设备物理状况（熔断逻辑判定），仅用于商城前端展示标签 |
| 价格独立计算 | 扣款金额独立于成色等级累加计算，等级不影响扣款数学 |
| 互不绑定 | 一台设备可能被定为 D 级（电池触发熔断），但其他维度扣款少时回收价依然可能较高；反之也可能 B 级但扣款多 |
**分离示例：**
- 设备 A：电池 78% → D 级，但其他维度完美（全原厂、外观无瑕、功能全正常），累计扣款仅电池 X4 = INR 4,000，基准价 INR 30,000，最终回收价 INR 26,000
- 设备 B：电池 88% → B 级（通过），但屏幕碎裂 A3 (3,500) + 边框变形 B3 (2,500) + 扬声器异常 F5 (800)，累计扣款 INR 6,800，同一基准价 INR 30,000，最终回收价 INR 23,200
- 结论：D 级的设备 A 回收价 (26,000) > B 级的设备 B (23,200)，这符合"等级是等级，价格是价格"的设计
##### 3.3.2.3.4 报价有效期

| 规则项 | 说明 |
|--------|------|
| 有效期 | 报价生成后 **30 分钟**内有效 |
| 超时处理 | 超时后用户仍未决策，报价自动失效，需重新质检生成新报价 |
| 有效期内报价不变 | 30 分钟内即使市场基准价后台更新，已生成报价不受影响 |
| 设计原因 | (1) 防止市场基准价更新导致报价不一致引发客诉；(2) 防止恶意比价套利（同一设备多门店比价） |
| 倒计时展示 | 平板和用户 App 均以倒计时形式展示剩余有效期，归零后页面变灰并提示"报价已失效，请联系店员重新质检" |

## 3.3.2.4 商城售价计算（销售侧定价）
商城售价在运营审核通过后、设备上架前由系统自动计算。售价计算的输入为设备回收价、设备成色等级、市场参考价，输出为商城挂牌售价。
**售价计算公式：**

```
理论售价 = 回收价 × (1 + 基准加价率)
最终商城售价 = clamp(理论售价, 售价下限, 售价上限)
其中：
  售价下限 = 回收价 × 1.05
  售价上限 = 市场参考价上限 × 1.0
  clamp(x, min, max) = max(min, min(x, max))

```
**定价参数（运营后台可配置）：**

| 参数 | 说明 | 默认值/示例 |
|------|------|------------|
| 基准加价率 | 基于回收价的基础浮动比例，覆盖平台佣金、运营成本、利润 | 15% - 35%（按成色等级分档） |
| 成色加价率阶梯 | 不同成色等级使用不同加价率 | 见下方对照表 |
| 市场参考价 | 该机型同成色在二手市场的参考售价区间 | 运营后台手动维护，P2 接入第三方数据 |
| 售价上限 (Ceiling) | 售价不得超过市场参考价上限，防止定价过高滞销 | 市场参考价上限 × 1.0 |
| 售价下限 (Floor) | 售价不得低于回收价 × 1.05，防止亏本 | 回收价 × 1.05 |
**定级与加价率对照（默认值，运营可调整）：**

| 成色等级 | 加价率 | 逻辑说明 |
|----------|--------|----------|
| A（99 新） | 35% | 近乎全新，可对标新机折价，溢价空间最大 |
| B（95 新） | 28% | 轻微使用痕迹，主流购买选择，利润率健康 |
| C（90 新） | 22% | 明显使用痕迹，性价比导向买家，合理利润 |
| D（85 新） | 15% | 大量瑕疵，价格敏感型买家，薄利快出策略 |
**计算示例：**

| 示例 | 设备 | 回收价 | 等级 | 加价率 | 理论售价 | 市场区间 | 最终售价 | 说明 |
|------|------|--------|------|--------|----------|----------|----------|------|
| #1 | iPhone 12 128GB | INR 15,000 | B | 28% | INR 19,200 | 18,000-23,000 | **INR 19,200** | 在区间内，直接采用 |
| #2 | iPhone 12 128GB | INR 25,000 | A | 35% | INR 33,750 | 20,000-30,000 | **INR 30,000** | 触发上限约束 |
| #3 | iPhone 12 128GB | INR 10,000 | C | 22% | INR 12,200 | 12,000-18,000 | **INR 12,200** | 在区间内 |
| #4 | iPhone 12 128GB | INR 5,000 | D | 15% | INR 5,750 | 6,000-10,000 | **INR 6,000** | 触发下限（市场下限 > 理论售价）|
**运营审核时的售价操作：**

| 操作 | 说明 |

| 修改记录 | 每次手动修改记录操作人、时间、修改前后价格、修改原因，写入审计日志 |

**售价的动态调整（P1 阶段实现）：**

| 规则项 | 说明 |
|--------|------|
| 滞销触发 | 设备上架后超过 N 天（默认 14 天）未售出 |
| 阶梯降价 | 每次自动降价 5%，最多降价 3 次 |
| 降价下限 | 累计降价不超过原始售价 × 0.85 (即 85 折) |
| 通知 | 每次降价后推送通知至相关运营人员 |

## 2.2 CLOUD-P0-02 核销确认

## 2.2.2 核销操作流程
**步骤 1：店老板录入金额**

```
用户接受报价
  → 系统推送通知至店老板 App："新的换购待处理"
  → 店老板点击进入价格录入页
  → 查看旧机抵扣金额（系统自动填入，只读）
  → 店老板手动输入：
      ├── 新机售价（INR，门店对新机的标价）
      └── 消费者实付金额（INR，消费者现场支付给门店的金额）
  → 系统实时校验：新机售价 - 抵扣金额 ?= 实付金额
      ├── 匹配（误差 = 0）→ 通过，提交成功 → 状态变更 [待用户 App 确认核销]
      └── 不匹配 → 展示差值，阻止提交，提示"金额不匹配，请核对"

```
**步骤 2：用户新手机登录**

```
状态进入 [待用户 App 确认核销]
  → 用户在新手机上安装/打开 App，用手机号 + OTP 登录
  → App 通过系统 API 自动读取新机信息：
      ├── 品牌/型号：Build.MANUFACTURER + Build.MODEL (Android) / utsname (iOS)
      └── IMEI/序列号：系统级 API 自动获取
  → App 将新机信息上报至中台
  → 中台关联新机信息至换购会话 session_id

```
**步骤 3：用户确认核销**

```
用户 App 展示核销确认摘要
  → 摘要内容：
      ├── 会话信息：换购会话 ID、店员姓名、质检时间
      ├── 旧机信息：品牌型号、IMEI（后四位）、成色等级、抵扣金额
      ├── 新机信息：品牌型号、IMEI（App 自动获取）、门店售价
      └── 结算校验：新机售价 - 旧机抵扣 = 实付金额 ✓
  → 用户点击"确认核销"
  → 系统二次确认弹窗："确认核销？确认后旧机回收将生效且无法撤回"
  → 用户确认 → 核销完成

```

## 2.2.3 核销成功后系统自动执行

| 序号 | 动作 | 说明 |
|------|------|------|
| 1 | 标记 verification.status = "confirmed" | 记录用户确认时间、新机信息（App 自动获取的） |
| 2 | 更新旧机状态 | device.status → "回收完成"，进入后续物流入库流程 |
| 3 | 生成换购凭证 (Trade-In Voucher) | 包含旧机信息 + 新机信息 + 抵扣金额 + 实付金额 + 店员 ID + 店老板 ID + 时间戳，用于门店对账和平台审计 |
| 4 | 推送完成通知 | 用户 App/H5 展示"核销成功"；店老板 App 和店员平板同步收到完成通知；平板提示"旧机交给 DB" |

## 2.2.4 防欺诈规则

| 编号 | 规则 | 说明 | 实现方式 |
|------|------|------|----------|
| AF-01 | 金额自动校验 | 新机售价 - 抵扣金 != 实付金额时系统拒绝提交 | 后端实时计算校验，不等误差，严格相等 |
| AF-02 | 新机信息 App 自动获取 | 品牌/型号/IMEI 由 App 从设备系统 API 读取，不可手动编辑 | 前端禁用输入，数据来源标记为 "system_api" |
| AF-03 | 双端确认 | 店老板录入金额 + 用户在新机 App 确认，双方见证 | 两阶段状态流转，缺一不可 |
| AF-04 | 一单一确 | 每次核销确认绑定唯一 session_id，不可跨会话使用 | session_id 唯一约束 |
| AF-05 | 审计日志 | 核销全链路记录：店老板录入 → 金额校验 → 用户新机登录确认 → 用户确认核销 | append-only 审计日志表 |
| AF-06 | 新机 IMEI 校验 | 用户登录的新机 IMEI 不能与平台上任何已有设备 IMEI 重复（防止店老板用已回收设备冒充新机） | 上报时实时查重，重复则告警并标记异常 |

| 关键字搜索 | IMEI（后四位）、型号关键词 | 模糊搜索 |

## 2.4.3 索引设计建议
```sql
-- 核心查询索引
CREATE UNIQUE INDEX idx_device_imei_hash ON device(imei_hash);
CREATE INDEX idx_device_status ON device(status);
CREATE INDEX idx_device_warehouse ON device(warehouse_id) WHERE warehouse_id IS NOT NULL;
CREATE INDEX idx_device_brand_model ON device(brand, model);
CREATE INDEX idx_device_grade ON device(appearance_grade);
CREATE INDEX idx_device_listed_at ON device(listed_at DESC) WHERE status = 'available_for_sale';
CREATE INDEX idx_device_price_sale ON device(price_sale) WHERE status = 'available_for_sale';
CREATE INDEX idx_device_store ON device(store_id);

```
**验收标准：**
- [ ] 每台设备以 IMEI hash 去重，同一 IMEI 不可重复创建
- [ ] 库存可按品牌/型号/成色/状态/仓库多维度组合查询
- [ ] 状态变更实时反映在库存查询结果中
- [ ] IMEI 在数据库中以 AES-256-GCM 加密存储，日志中脱敏
- [ ] 复合查询（品牌+型号+成色+价格区间）响应时间 < 3 秒
- [ ] 并发更新场景下乐观锁 (version) 正确阻止脏写

## 2.5 CLOUD-P0-05 5 分钟独占锁
**优先级：** P0
**功能描述：**
用户点击"立即购买"后，系统对该 IMEI 设备开启独占锁，锁定时长 5 分钟（300 秒）。锁定期间其他用户不可购买该设备。超时未支付自动释放锁，设备恢复可售。

## 2.5.1 锁机制设计

| 设计点 | 方案 |
|--------|------|
| 锁类型 | 悲观锁（Redis SETNX + TTL） |
| 锁键格式 | `device_lock:{imei_hash}` |
| 锁值 | `{order_id}:{user_id}` |
| TTL | 300 秒（5 分钟） |
| 过期行为 | Redis key 过期后，通过 Redis Keyspace Notification 回调或定时任务轮询，将设备状态从"付款中"回退至"在库可售" |
**加锁流程：**

```
用户点击"立即购买"
  → 检查设备状态是否为 "available_for_sale"
      ├── 否 → 返回错误："该设备不可购买，当前状态：{status}"
      └── 是 → 继续
  → 执行 Redis SETNX device_lock:{imei_hash} {order_id}:{user_id} EX 300
      ├── 成功 (返回 1) → 加锁成功
      │     → 更新 device.status = "payment_in_progress"
      │     → 创建订单 (status = "pending_payment")
      │     → 返回订单确认页数据 + 锁倒计时
      └── 失败 (返回 0) → 锁已存在
            → 检查锁值中的 user_id 是否为当前用户？
                ├── 是 → 返回已有订单（支持重新进入支付页）
                └── 否 → 返回错误："该设备已被其他用户锁定，请浏览其他设备"

```
**释放锁流程：**

```
触发释放的三种情况：
  1. 支付成功 → 删除锁 → device.status = "sold"（锁变更为永久占有）
  2. 用户主动取消 → 删除锁 → device.status = "available_for_sale"
  3. TTL 过期（300 秒） → Redis Keyspace Notification 或定时任务
       → 检测订单状态仍为 "pending_payment"
       → 更新 device.status = "available_for_sale"
       → 更新 order.status = "expired"

```
## 2.5.2 业务规则

| 规则项 | 说明 |
|--------|------|
| 锁定时长 | 300 秒（5 分钟），不可延长 |
| 锁粒度 | IMEI 级别，一设备一锁 |
| 释放方式 | 支付成功 / 用户主动取消 / 超时自动释放 |
| 并发安全 | Redis SETNX 保证原子性，只有第一个请求能获取锁 |
| 续锁 | **不支持**续锁，5 分钟不可延长 |
| 锁信息展示 | 订单确认页展示实时倒计时，归零后自动跳转至"订单已超时"页 |
| 重试策略 | 锁释放后设备恢复可售，原用户或新用户均可再次发起购买 |
| 支付失败 | 支付失败不释放锁，在锁定期间内可重新支付 |
## 2.5.3 锁状态检查
```json
// GET /api/v1/devices/{device_id}/lock-status
{
  "device_id": "UUID",
  "is_locked": true,
  "locked_by_current_user": false,
  "lock_remaining_seconds": 180,
  "lock_order_id": "UUID|null"
}

```
**验收标准：**
- [ ] 锁定成功后，其他用户请求同一设备返回"已被锁定"
- [ ] 300 秒后锁自动释放，设备状态恢复"在库可售"
- [ ] 支付成功后锁变更为永久（设备状态变为"已售"），不会超时释放
- [ ] 用户主动取消后锁立即释放
- [ ] 并发场景下只有一个用户能获取锁（SETNX 原子性保证）
- [ ] 同一用户的同一设备不可重复创建订单（锁值中的 user_id 校验）
- [ ] 支付失败后 5 分钟内可继续在同一订单重试支付

## 2.6 CLOUD-P0-06 Razorpay 支付集成
**优先级：** P0
**功能描述：**
集成 Razorpay 支付网关，支持 UPI Intent 支付方式（Google Pay、PhonePe 等）。支付流程分为服务端创建订单、App 端唤起 SDK 支付、异步 Webhook 回调处理三个阶段。

## 2.6.1 支付流程

```
第一阶段：服务端创建 Razorpay Order
─────────────────────────────────────
  中台接收下单请求
    → 校验设备锁有效性
    → 计算订单金额 (INR, 单位 paise: ×100)
    → 调用 Razorpay Orders API:
        POST https://api.razorpay.com/v1/orders
        {
          amount: 1920000,        // INR 19,200 × 100
          currency: "INR",
          receipt: "order_{uuid}",
          notes: {
            device_id: "...",
            order_id: "..."
          }
        }
    → Razorpay 返回 razorpay_order_id
    → 中台存储 razorpay_order_id 至本地订单
    → 返回 razorpay_order_id + amount + currency + key_id 至 App
第二阶段：App 端唤起 Razorpay Checkout SDK
──────────────────────────────────────────
  App 收到订单数据
    → 构建 Razorpay Checkout options:
        {
          key: key_id,
          amount: 1920000,
          currency: "INR",
          order_id: razorpay_order_id,
          prefill: { contact, email },
          method: { upi: {} }
        }
    → 调用 Razorpay.open()
    → 用户选择 UPI App (Google Pay / PhonePe 等)
    → 完成付款
    → Razorpay SDK 返回 payment_id
第三阶段：服务端处理 Webhook 回调
─────────────────────────────────
  Razorpay 异步 POST webhook 至中台
    POST /api/v1/webhooks/razorpay
    Headers: X-Razorpay-Signature
    Body: { event: "payment.captured", payload: { payment: { entity: {...} } } }
    → 中台验证 Webhook 签名:
        computed_signature = HMAC-SHA256(webhook_body, webhook_secret)
        if computed_signature !== X-Razorpay-Signature:
            → 丢弃请求，记录告警日志，返回 400
        else:
            → 签名有效，继续处理
    → 解析 payload，获取 payment_id, order_id, status
    → 调用 Razorpay API 二次验证支付状态 (GET /payments/{payment_id})
    → 确认支付已 captured 后：
        ├── 更新本地 order.status = "paid"
        ├── 更新 device.status = "sold"
        ├── 释放 Redis 独占锁
        ├── 触发智能路由引擎 (CLOUD-P0-07)
        └── 返回 200 OK 至 Razorpay

```

## 2.6.3 业务规则

| 规则项 | 说明 |
|--------|------|
| Webhook 签名验证 | 使用 Razorpay Webhook Secret 对请求体做 HMAC-SHA256，验证不通过则丢弃 |
| 二次验证 | Webhook 收到后必须调用 Razorpay GET Payments API 二次确认支付状态，不信任 Webhook 单一来源 |
| 幂等处理 | 同一 razorpay_payment_id 的 Webhook 重复推送不予重复处理 |
| 超时处理 | 订单创建后 5 分钟内未收到 Webhook 且未主动查询，订单状态标记为 expired |
| 主动查询 | App 端在支付 SDK 回调后，主动调用支付状态查询接口确认结果（不依赖 Webhook 推送延迟） |
| 退款 | 售后退款通过 Razorpay Refunds API 原路退款至用户 UPI 账户 |
**验收标准：**
- [ ] 服务端成功创建 Razorpay Order 并返回 order_id
- [ ] App 端成功唤起 Razorpay Checkout SDK
- [ ] 支付成功 Webhook 在 30 秒内到达
- [ ] Webhook 签名验证通过后才更新订单状态
- [ ] 签名验证失败不更新订单、记录告警日志
- [ ] 同一 payment_id 的重复 Webhook 不重复处理
- [ ] 支付失败后用户在 5 分钟锁定期间内可在同一订单重试
- [ ] 退款通过 Razorpay Refunds API 原路退回

## 2.7 CLOUD-P0-07 智能路由引擎
**优先级：** P0
**功能描述：**
支付成功后，根据购买订单中的设备 IMEI 反查库存，定位设备当前所在的区域总仓库，并向该仓库下发出库通知。

## 2.7.1 路由流程

```
支付成功 Webhook 验证通过
  │
  ├── 获取订单中的设备列表 [device_id_1, device_id_2, ...]
  │
  ├── 判断订单类型：
  │     ├── B2C 个人订单：
  │     │     → 设备只有一个
  │     │     → 以 IMEI 反查 warehouse_id
  │     │     → 1:1 路由至该仓库
  │     │     → 向仓库推送出库任务
  │     │
  │     └── B2B 批量订单：
  │           → 设备有多个
  │           → 逐台以 IMEI 反查 warehouse_id
  │           → 按 warehouse_id 聚合分组
  │           → 对每组生成一个子订单
  │           → 向各仓库分别推送出库任务
  │
  ├── 路由成功后：
  │     → 订单状态 = "paid" (保持不变)
  │     → 设备状态保持 "sold"
  │     → 创建出库任务 (warehouse_outbound_task)
  │
  └── 路由失败（反查不到仓库）：
        → 订单标记 "routing_error"
        → 发送告警通知至运营
        → 人工介入处理

```

## 2.7.2 业务规则

| 规则项 | 说明 |
|--------|------|
| 触发时机 | 收到 Razorpay 支付成功 Webhook 且签名验证通过后 |
| 路由逻辑 | 以 IMEI → 反查 `warehouse_id`，一对一映射 |
| B2C 路由 | 单台设备直接路由至所在仓库 |
| B2B 路由 | 多台设备按仓库聚合拆分后，分别路由各仓库（详见 CLOUD-P1-04） |
| 出库通知 | 向仓库端推送出库任务：含设备信息、订单号、收件地址、快递面单数据 |
| 异常处理 | 反查不到 warehouse_id 时，订单标记 `routing_error`，人工介入 |
| 性能要求 | 支付确认后 5 秒内完成路由并下发仓库通知 |

## 2.7.3 出库任务数据模型
```json
{
  "outbound_task_id": "UUID",
  "order_id": "UUID",
  "sub_order_id": "UUID|null",
  "device_id": "UUID",
  "imei": "string (encrypted)",
  "brand": "string",
  "model": "string",
  "condition_grade": "A|B|C|D",
  "warehouse_id": "UUID",
  "recipient_name": "string",
  "recipient_phone": "string (encrypted)",
  "recipient_address": "string",
  "recipient_city": "string",
  "recipient_pincode": "string",
  "shipping_label_url": "string|null",
  "status": "pending|picked|packed|shipped",
  "assigned_operator_id": "UUID|null",
  "created_at": "ISO8601"
}

```
**验收标准：**
- [ ] 支付成功后 5 秒内完成路由并下发仓库出库通知
- [ ] B2C 订单 1:1 正确路由至设备所在仓库
- [ ] B2B 订单正确拆分为按仓库聚合的子订单
- [ ] 反查不到仓库时订单标记 `routing_error` 并告警，不丢失订单数据
- [ ] 路由失败的订单在运营后台可见，支持人工重新路由

## 2.8 CLOUD-P0-09 多语言国际化 (i18n)
**优先级：** P0
**功能描述：**

## 2.10 CLOUD-P0-12 OTP 验证服务
**优先级：** P0
**功能描述：**
店员输入用户手机号后，系统生成 6 位随机 OTP 并发送 SMS（含 H5 短链）。店员在平板输入用户告知的 OTP，系统验证通过后完成身份确认并自动创建到店会话。

## 2.10.1 OTP 生命周期

```
[已生成]
  │
  ├── 3 分钟内输入正确 ──────→ [已验证] (终态，同时创建会话)
  │
  ├── 3 次输入错误 ──────→ [已锁定 60s] ──(60s后)──→ 可重新发送
  │
  └── 3 分钟超时 ──────→ [已过期] → 可重新发送

```

## 2.10.2 OTP 生成与发送
**OTP 生成规则：**

| 参数 | 说明 |
|------|------|
| 长度 | 6 位数字 (000000 - 999999) |
| 随机性 | 使用密码学安全随机数生成器 (CSPRNG) |
| 有效期 | 3 分钟（生成后 3 分钟内有效） |
| 存储 | Redis: `otp:{phone_hash}` → `{otp_value}:{session_id}:{attempts}`，TTL = 60s |
| 每日上限 | 同一手机号每日最多生成 5 次 OTP |
**SMS 发送：**

| 设计点 | 说明 |
|--------|------|
| 发送渠道 | SMS（优先），WhatsApp Business API（备选） |
| SMS 模板 | 见下方 |
| 送达时间 | 3 秒内 |
| 发送失败处理 | 自动切换至备用渠道（WhatsApp），两者均失败则提示店员"发送失败，请重试" |
**SMS 模板：**

```
[Platform] OTP: XXXXXX
Track: bott.in/s/abc123
Valid 60s. Do not share.
आपका OTP: XXXXXX

```

## 2.10.3 OTP 验证流程

```
店员在平板输入 6 位 OTP
  │
  ├── 查询 Redis: otp:{phone_hash}
  │     ├── 不存在 → "OTP 已过期，请重新发送"
  │     └── 存在 → 获取 {otp_value, session_prefix, attempts}
  │
  ├── 校验 attempts:
  │     ├── attempts >= 3 → 锁定 60 秒
  │     │     → 设置 Redis: otp_lock:{phone_hash}，TTL = 60s
  │     │     → 返回 "验证次数过多，请 60 秒后重试"
  │     └── attempts < 3 → 继续验证
  │
  ├── 校验 OTP 值：
  │     ├── 匹配 → 验证通过
  │     │     → 删除 Redis otp key
  │     │     → 触发 CLOUD-P0-10 会话创建流程
  │     └── 不匹配 → attempts++
  │           → 更新 Redis: otp:{phone_hash}
  │           → 返回 "验证码错误，剩余重试次数：{3 - attempts}"
  │
  └── 每日上限检查（发送时已做）

```

## 2.10.4 业务规则汇总

| 编号 | 规则项 | 说明 |
|------|--------|------|
| OTP-01 | OTP 长度 | 6 位数字 |
| OTP-02 | 有效期 | 3 分钟，过期需重新发送 |
| OTP-03 | 最大重试 | 3 次；超过后锁定 60 秒 |
| OTP-04 | 每日上限 | 同一手机号每日最多 5 次发送 |
| OTP-05 | 发送渠道 | SMS（优先）；WhatsApp Business API（备选） |
| OTP-06 | OTP 即授权 | OTP 验证通过即表示用户同意质检，不再需要单独授权页 |
| OTP-07 | 冷却锁定 | 3 次错误后锁定 60 秒，60 秒后自动解除，可重新发送 |
| OTP-08 | 每日重置 | 每日上限以 UTC+5:30 (IST) 自然日重置 |

## 2.10.5 Redis 数据结构

```
## OTP 存储
Key:   otp:{phone_sha256}
Value: {otp_value}:{session_prefix}:{attempts}
TTL:   60s
## 锁定标记
Key:   otp_lock:{phone_sha256}
Value: {locked_at_timestamp}
TTL:   60s
## 每日发送计数
Key:   otp_daily_count:{phone_sha256}
Value: {count}
TTL:   到当天 IST 24:00 的剩余秒数

```
**验收标准：**
- [ ] 生成 OTP 后 3 秒内 SMS 送达
- [ ] 正确 OTP 验证通过，错误 OTP 提示重试并显示剩余次数
- [ ] 3 次错误后锁定 60 秒，锁定期间不可重试/重发
- [ ] 60 秒后自动解除锁定，可重新发送
- [ ] 每日超限（5 次）提示"今日验证次数已达上限"
- [ ] SMS 发送失败时自动切换至 WhatsApp 备用渠道
- [ ] OTP 验证通过后自动触发会话创建

## 2.12 CLOUD-P0-14 统一登录与多角色会话管理

**优先级：** P0

**功能描述：**
门店综合 App 使用统一登录入口，所有角色（店老板/库管/DB）共用同一登录接口。服务端验证手机号+密码（或 OTP）后，返回该账号的角色列表及对应权限，App 根据角色加载对应模块。同一账号可拥有多个角色，服务端维护角色切换时的独立会话状态。

**登录接口响应模型：**
```json
{
  "user_id": "U-xxxx",
  "name": "Rajesh Kumar",
  "phone": "+919876543210",
  "token": "jwt-token-xxxx",
  "roles": [
    {
      "role": "owner",
      "store_id": "ST001",
      "store_name": "Mumbai Central",
      "permissions": ["verification", "staff_mgmt", "revenue", "b2b_purchase"]
    },
    {
      "role": "warehouse",
      "warehouse_id": "WH002",
      "warehouse_name": "Mumbai Main WH",
      "permissions": ["checkin", "refurbish", "outbound", "scan_imei", "print_label", "inventory"]
    }
  ],
  "default_role": "owner"
}
```

**角色切换 API：**
```
POST /api/v1/auth/switch-role
Request: { "role": "warehouse" }
Response: { "token": "new-jwt-token", "role": "warehouse", ... }
```
切换角色时服务端生成新的 JWT token，包含目标角色的权限声明。原角色 token 仍然有效。

**业务规则：**
| 规则项 | 说明 |
|--------|------|
| 登录验证 | 手机号+密码（主）；手机号+OTP（备用）；密码需满足 8-20 位、至少两类字符 |
| 角色返回 | 服务端根据 `user_roles` 表返回该账号的所有已启用角色；含对应的门店/仓库信息和权限列表 |
| 多角色 JWT | 每个角色独立 JWT token；token payload 中包含 `role` 和 `store_id`/`warehouse_id` |
| 角色切换 | 无需重新登录；服务端生成新角色 JWT；旧 token 不受影响 |
| 权限即时生效 | 运营后台修改权限后，用户下次切换角色时权限生效；若当前 token 有效期内权限被撤销，token 仍然有效直至过期（最长 2 小时） |
| 会话超时 | 30 分钟无操作自动失效；所有角色 token 共享同一超时计时器 |
| 设备绑定 | 一个账号最多 3 台设备同时登录；运营后台可强制踢出特定设备 |

**权限拦截中间件：**
每个 API 请求通过 JWT token 中的 `role` 和 `permissions` 字段进行鉴权：
- 店老板角色不可访问仓库出库 API
- 库管角色不可访问授信结算 API
- DB 角色不可操作门店质检数据
- 同一 API 端点可被多个角色访问（如设备详情查询）

**验收标准：**
- [ ] 手机号+密码登录返回角色列表和 JWT token
- [ ] 多角色账号可切换角色，切换后 token 权限正确
- [ ] 店老板角色 API 不可被库管 token 访问
- [ ] 运营修改权限后，2 小时内新 token 生效
- [ ] 30 分钟无操作全部角色 token 失效
- [ ] 强制踢出后当前 token 立即失效

### 2.12.1 编码体系

| 实体 | 格式 | 示例 | 说明 |
|------|------|------|------|
| 门店 | `ST-{州码2位}-{4位序号}` | `ST-MH-0001` | 印度邦/直辖区双字母代码：MH(马哈拉施特拉), DL(德里), KA(卡纳塔克), TN(泰米尔纳德), GJ(古吉拉特), UP(北方邦), WB(西孟加拉), RJ(拉贾斯坦) |

### 2.12.5 账号生命周期状态机

```
                    SA/OWN 创建账号
                          │
                          ▼
          ┌──────────────────────────────┐
          │     pending_activation       │  ← 待激活
          │   (7天有效期，超时自动清理)    │
          └──────────────┬───────────────┘
                         │ 用户首次登录 + 设置密码 + 同意协议
                         ▼
          ┌──────────────────────────────┐
          │          active              │  ← 正常使用
          └──────┬──────────┬────────────┘
                 │          │
    5次密码错误  │          │ SA/OWN 主动禁用
                 ▼          ▼
          ┌──────────┐  ┌──────────────┐
          │  locked  │  │   disabled   │  ← 可重新启用
          │ (15分钟)  │  └──────────────┘
          └────┬─────┘
               │ 15分钟后自动解锁
               ▼
          ┌──────────┐
          │  active  │  ← 回到正常
          └──────────┘

          ┌──────────────┐
          │   removed    │  ← OWN 移除店员（不可逆）
          └──────────────┘

          ┌──────────────┐
          │   deleted    │  ← 用户主动注销（30天冷静期后可永久删除）
          └──────────────┘
```

**状态定义：**

| 状态 | 含义 | 可流转至 | 说明 |
|------|------|----------|------|
| `pending_activation` | 待激活 | active | 账号已创建但用户未登录激活；7 天后自动清理 |
| `active` | 正常 | locked, disabled, removed, deleted | 可正常使用所有功能 |
| `locked` | 临时锁定 | active | 5次密码错误自动锁定 15 分钟 |
| `disabled` | 已禁用 | active | 管理员主动禁用，可重新启用 |
| `removed` | 已移除 | —（终态） | 店员被移除，不可逆，历史数据保留 |
| `deleted` | 已注销 | —（终态） | 用户主动注销，30天冷静期后永久删除 PII |

**验收标准：**
- [ ] SA 可创建店老板账号，系统自动发送邀请 SMS
- [ ] 店老板可添加店员，系统校验权限和门店归属
- [ ] 首次登录（临时密码）强制激活：设置新密码 + 同意协议
- [ ] 临时密码仅可使用一次
- [ ] 7 天未激活账号自动清理
- [ ] 忘记密码：OTP 验证 → 重置密码 → 所有 token 失效
- [ ] 密码规则：8-20 位，至少含大写字母 + 数字
- [ ] 连续 5 次密码错误锁定 15 分钟，锁定期间 OTP 登录也禁用
- [ ] 店员数量上限可配置（默认 10 人/店）
- [ ] 账号生命周期状态机正确流转
- [ ] 密码修改后所有设备 JWT 立即失效

## 3.2 CLOUD-P1-02 同城货源算法
**优先级：** P1
**功能描述：**
根据用户所在城市，匹配同城仓库的在库设备优先展示。当同城设备不足时，扩展至全国范围补充展示。同城商品标注"同城"标签，排序权重高于非同城商品。

## 3.2.1 排序权重模型
**排序公式：**

```
综合得分 = (同城匹配 × 1.5) + (入库时间因子 × 1.2) + (上架时间因子 × 1.0) + (成色等级因子 × 0.8)

```

| 权重因子 | 权重值 | 计算方式 | 说明 |
|----------|--------|----------|------|
| 同城匹配 | 1.5 | 设备所在仓库城市 == 用户城市 → 1.0；否则 → 0 | 同城优先展示 |
| 入库时间 (FIFO) | 1.2 | 归一化后的入库时间排名（越早入库得分越高） | 库存先进先出，减少滞销 |
| 上架时间 | 1.0 | 归一化后的上架时间排名（越晚上架得分越高） | 新上架设备获得一定曝光 |
| 成色等级 | 0.8 | A=1.0, B=0.8, C=0.6, D=0.4 | 高成色设备略优先 |

## 3.2.2 同城匹配规则

| 规则项 | 说明 |
|--------|------|
| 城市判定 | 基于用户定位（IP 地理定位 或 手动选择城市）匹配仓库所在城市 |
| 同城标签 | 设备卡片展示"同城"标签，增强用户信任感 |
| 同城阈值 | 同城设备 < 10 台时，自动补充全国范围的设备 |
| 全国补充 | 全国设备按综合得分降序排列，不受同城权重影响（同城因子为 0） |
| 排名实时 | 每次商城列表查询时实时计算排序得分 |

- [ ] 全国补充设备不受同城权重影响
- [ ] 用户可手动切换城市

## 3.3 CLOUD-P1-03 B2B 批量锁单
**优先级：** P1
**功能描述：**
门店（企业采购模式）批量下单时，对购物车内所有设备同时加锁。锁定时长 5 分钟（300 秒）。若有任一设备锁定失败（已被他人锁定），整个批量下单失败并提示具体失败设备。

## 3.3.1 批量加锁流程

```
B2B 批量下单请求
  │
  ├── 校验购物车所有设备状态 == "available_for_sale"
  │     ├── 有设备不可售 → 返回具体设备清单 + 失败原因
  │     └── 全部可售 → 继续
  │
  ├── 开始批量加锁：
  │     → 逐台执行 Redis SETNX device_lock:{imei_hash} {order_id}:{user_id} EX 300
  │     │
  │     ├── 全部加锁成功 → 继续下单
  │     │     → 批量更新所有设备 status = "payment_in_progress"
  │     │     → 创建合并订单
  │     │     → 返回订单确认页
  │     │
  │     └── 任一台加锁失败 → 全部回滚
  │           → 释放已加锁设备（DELETE Redis key）
  │           → 回滚已更新的设备状态
  │           → 返回失败清单：
  │               {
  │                 "success": false,
  │                 "error": "BATCH_LOCK_FAILED",
  │                 "failed_devices": [
  │                   {
  │                     "device_id": "UUID",
  │                     "brand": "Samsung",
  │                     "model": "Galaxy S21",
  │                     "reason": "locked_by_another_user"
  │                   }
  │                 ],
  │                 "locked_devices_released": 4
  │               }
  │
  └── 订单超时 (300s) 或用户取消：
        → 批量释放所有锁
        → 批量回退所有设备 status = "available_for_sale"

```

## 3.3.2 原子性保证

| 策略 | 实现方式 |
|------|----------|
| 全或无 | 使用数据库事务 + Redis Pipeline 组合，确保批量锁的原子性 |
| 回滚机制 | 任一台加锁失败时，立即释放已获取的所有锁 |
| 超时释放 | 所有锁共享 300 秒 TTL，超时后自动统一释放 |
| 并发安全 | Redis pipeline 批量执行 SETNX，减少加锁窗口期 |
**验收标准：**
- [ ] 全部设备锁定成功才允许进入支付
- [ ] 任一设备锁定失败则整单回滚，已锁定设备立即释放
- [ ] 超时后所有设备锁同时释放
- [ ] 并发场景下不出现部分锁定成功部分失败的情况
- [ ] 失败时明确返回具体失败设备和原因

## 3.4 CLOUD-P1-04 B2B 子订单拆分
**优先级：** P1
**功能描述：**
B2B 批量订单支付成功后，中台按设备所在仓库进行聚合拆分，生成多个子订单。每个子订单对应一个仓库，包含该仓库需出库的设备列表。对 B2B 采购方（门店）透明，仍以合并订单作为主视图。

## 3.4.1 拆分流程

```

  │
  ├── 获取订单中所有 device_id 列表
  │
  ├── 逐台查询 device.warehouse_id
  │     → [device_1: WH-A, device_2: WH-A, device_3: WH-B, device_4: WH-C, device_5: WH-B]
  │
  ├── 按 warehouse_id 聚合：
  │     ├── WH-A: [device_1, device_2] → 子订单 #1
  │     ├── WH-B: [device_3, device_5] → 子订单 #2
  │     └── WH-C: [device_4]           → 子订单 #3
  │
  ├── 每个子订单：
  │     ├── 生成 sub_order_id
  │     ├── 关联 parent_order_id
  │     ├── 指定 warehouse_id
  │     ├── 计算子订单金额（该仓库设备售价之和）
  │     └── 创建出库任务至对应仓库
  │
  └── 物流追踪以子订单为单位

```

## 3.5 CLOUD-P1-06 B2B 授信额度管理
**优先级：** P1
**功能描述：**
平台可为门店企业采购账号配置授信额度。门店在 B2B 批量下单时可选择"直接企业支付"（Razorpay 在线付款）或"授信金额支付"（从授信额度中扣减）。授信额度由运营后台统一管理和调整，授信支付的订单标记为"待结算"，DB 端后续进行统一结算对账。

## 3.5.1 授信额度模型

| 字段 | 数据类型 | 说明 |
|------|----------|------|
| `credit_id` | UUID (PK) | 授信记录 ID |
| `store_id` | UUID (FK) | 门店 ID |
| `total_credit_inr` | INTEGER | 授信总额度（INR），运营后台配置 |
| `used_credit_inr` | INTEGER | 已用额度：已通过授信支付但尚未结算的累计金额 |
| `frozen_credit_inr` | INTEGER | 冻结额度：授信订单已确认但 DB 尚未结算的金额（在途资金） |
| `available_credit_inr` | INTEGER (计算字段) | 可用额度 = total_credit - used_credit - frozen_credit |
| `status` | ENUM | active / frozen / closed |
| `credit_limit_updated_by` | UUID | 额度修改人 |
| `credit_limit_updated_at` | TIMESTAMP | 额度修改时间 |
| `created_at` | TIMESTAMP | 授信开通时间 |

## 3.5.2 授信支付流程

```
B2B 确认批量下单 → 选择支付方式
  │
  ├── [直接企业支付] (default)
  │     → Razorpay 在线付款流程（同 CLOUD-P0-06）
  │     → 支付成功 → 订单确认 → 智能路由
  │
  └── [授信金额支付]
        │
        ├── 系统校验：available_credit >= 订单金额？
        │     ├── 是 → 继续
        │     └── 否 → 拒绝支付：
        │           {
        │             "error": "CREDIT_INSUFFICIENT",
        │             "available_credit_inr": 50000,
        │             "order_amount_inr": 75000,
        │             "shortfall_inr": 25000,
        │             "suggestion": "请切换至直接支付或联系运营提高授信额度"
        │           }
        │
        ├── 扣减授信额度：
        │     → frozen_credit += 订单金额
        │     → available_credit = total_credit - used_credit - frozen_credit
        │
        ├── 订单确认：
        │     → order.payment_method = "credit"
        │     → order.settlement_status = "pending_settlement"
        │
        └── 后续结算（由 DB 端完成，见下文）

```

## 3.5.3 授信结算生命周期

```
[授信订单已发货]
  │
  ├── DB 查看待结算授信订单列表（按发货时间排序）
  │
  ├── DB 发起结算：
  │     → 支持多选批量结算
  │     → 结算方式：银行转账 / Razorpay 补付
  │     → 门店完成付款
  │     → DB 点击"确认已收款"
  │
  ├── 系统执行结算：
  │     → used_credit -= 本次结算金额（若已结算金额 >= 订单金额，全部释放）
  │     → frozen_credit -= 结算金额
  │     → order.settlement_status = "settled"
  │     → 记录结算日志
  │
  └── 逾期处理：
        → 超过结算周期（如 T+15）未付款
        → 订单标记 settlement_status = "overdue"
        → 门店授信 status = "frozen"（冻结，不可继续授信支付）
        → 推送逾期通知至店老板 App 和 DB

```

## 3.5.4 业务规则

| 编号 | 规则项 | 说明 |
|------|--------|------|
| CR-01 | 额度配置 | 运营后台按门店配置授信总额度，修改记录操作人和时间戳 |
| CR-02 | 额度校验 | 每次授信支付前实时校验可用额度，不足时拒绝支付并展示具体差额 |
| CR-03 | 冻结机制 | 授信订单确认后立即冻结对应金额（frozen_credit），防止超额使用 |
| CR-04 | 结算周期 | DB 端根据与门店约定的结算周期发起结算（默认 T+15） |
| CR-05 | 逾期冻结 | 超过结算周期未付款的授信订单，系统标记"逾期"并冻结该门店的授信额度 |
| CR-06 | 额度调整 | 运营后台调整授信总额度时，若新额度 < (used + frozen)，拒绝调整 |
| CR-07 | P2 扩展 | 若订单金额超过可用额度，门店可部分授信+部分直接支付（P2 阶段实现） |

| 乐观锁 | 所有可能并发更新的表使用 version 字段做乐观锁控制 |
| 软删除 | 核心业务表使用 deleted_at 字段实现软删除 |
| JSONB | 灵活结构数据（扣款明细、质检数据快照、审核调整）使用 JSONB 存储 |
| 审计日志 | 所有关键写操作同步写入 audit_log 表 |
| 索引策略 | 以查询模式驱动索引设计，避免过度索引 |
