## 一、设计理念
## 1.1 为什么统一

| 维度 | 多个独立端 | 一个跨端应用 |
|------|:---:|:---:|
| 开发维护 | 多份代码库，多条 CI/CD | 1 份代码库，跨端编译（App + Web） |
| 发布更新 | 多个 App Store + Web 部署 | 1 套代码，多端发布 |
| 多角色用户 | 装多个 App / 登录多个后台 | 1 个应用，切换角色/视图 |
| 账号管理 | 多套登录 | 1 套登录，权限控制可见模块 |
| 权限管理 | 多套角色配置 | 1 套权限矩阵，勾选即可 |
**核心原则**：一套代码，跨端编译（App + Web），角色决定界面。管理员开通账号时勾选角色权限，应用动态加载对应模块。

## 三、账号与登录

## UA-P0-01 统一登录
**优先级：** P0
**功能描述：**
所有角色使用同一登录入口。输入手机号 + 密码（或 OTP）登录，服务端返回该账号的角色列表和对应权限编码。若该账号只有一个角色，直接进入该角色视图；若有多个角色，展示角色选择页。
**登录流程：**

```
打开 App → 登录页（展示 Dobara 品牌 Logo）
  → 输入手机号（印度 +91 前缀固定展示，输入 10 位数字）
  → 输入密码（支持切换为 OTP 登录）
  → 点击"登录"
  → 服务端验证：
      ├── 账号不存在 → "账号不存在，请联系管理员开通"
      ├── 账号已禁用 → "账号已被停用，请联系管理员"
      ├── 密码错误 → "密码错误，剩余重试 N 次"（5 次锁定 15 分钟）
      ├── 账号待激活（首次登录）→ "请先设置您的密码"→ 进入密码设置页
      └── 验证通过 → 返回完整登录响应
```

**登录页面的三种入口：**

| 入口 | 说明 |
|------|------|
| 密码登录（默认） | 手机号 + 密码，登录按钮 |
| OTP 登录（切换） | 手机号 → 发送 OTP（6位/3分钟）→ 输入 OTP → 验证通过 |
| 忘记密码 | "忘记密码？"→ 输入手机号 → OTP 验证 → 设置新密码 → 重新登录 |

**首次登录——强制激活流程：**

```
SA/店老板创建账号后，系统发送邀请 SMS（含临时密码）
  → 用户下载 App，输入手机号 + 临时密码
  → 服务端检测 account_status = "pending_activation"
  → 强制跳转密码设置页：
      ├── 输入新密码（8-20 位，至少含大写字母+数字两类字符）
      ├── 确认新密码
      ├── 勾选同意用户协议和隐私政策
      └── 点击"激活账号"
  → 服务端：
      ├── 更新 password_hash
      ├── 更新 account_status = "active"
      ├── 记录 activated_at 时间戳
      └── 返回完整登录响应（含角色+权限）
  → App 进入角色首页
```

**业务规则：**

| 规则项 | 说明 |
|--------|------|
| 登录方式 | 手机号 + 密码（主）；手机号 + OTP（备用，3分钟有效） |
| 密码规则 | 8-20 位，至少含大写字母 + 数字两类字符；禁止与手机号相同 |
| 密码修改 | 需输入旧密码 + 新密码 + 确认新密码；修改后所有设备 token 失效，需重新登录 |
| 登录失败锁定 | 连续 5 次密码错误 → 锁定 15 分钟；锁定期间"登录"按钮置灰 + 展示倒计时 |
| 角色返回 | 服务端根据 `user_role_assignment` 表返回该账号的所有已启用角色及对应门店/仓库信息 |
| 多角色切换 | App 内左上角头像 → "切换角色"，无需重新登录（详见 UA-P0-02） |
| 权限即时生效 | 管理员修改权限后，用户下次切换角色或重新登录时权限生效 |
| 会话超时 | 30 分钟无操作自动退出；所有角色共享同一超时计时器 |
| 设备绑定 | 一个账号最多同时在 3 台设备登录；管理员可强制踢出特定设备 |
| JWT Token | 每个角色独立 JWT；payload 中含 `role_code`、`org_id`、`permissions[]`、`exp` |
| Token 刷新 | Token 过期前 5 分钟自动刷新；刷新失败需重新登录 |

**忘记密码流程：**

```
App 登录页 → 点击"忘记密码？"
  → 输入手机号（必须与注册手机号一致）
  → 点击"发送验证码"
  → 系统发送 6 位 OTP（3 分钟有效）
  → 输入 OTP → 验证通过
  → 进入设置新密码页：
      ├── 输入新密码（8-20 位，至少两类字符）
      ├── 确认新密码
      └── 点击"确认修改"
  → 服务端更新密码 → 所有设备 token 失效
  → 返回登录页："密码修改成功，请使用新密码重新登录"
```

**验收标准：**
- [ ] 手机号+密码登录成功，服务端返回角色列表 + 权限编码
- [ ] 手机号格式校验：10 位印度手机号，非法格式即时提示
- [ ] 单角色直接进入对应首页，多角色展示选择页
- [ ] 连续 5 次密码错误锁定 15 分钟，展示倒计时
- [ ] 首次登录（临时密码）强制跳转密码设置页 + 协议确认
- [ ] 临时密码仅可使用一次（登录成功后失效）
- [ ] 忘记密码：OTP 验证通过后可设置新密码，旧密码立即失效
- [ ] 密码修改后所有设备 token 失效，需重新登录
- [ ] App 内切换角色无需重新登录（详见 UA-P0-02）
- [ ] 权限即时生效
- [ ] 30 分钟超时自动退出
- [ ] 账号被禁用后 5 分钟内当前会话自动登出
- [ ] Token 过期前 5 分钟自动刷新

## 四、管理员角色模块（SA）

> 管理员（ROLE-SA）由系统初始化创建，含原运营（OPS）的全部能力。管理员登录内部业务应用后进入 SA 视图，负责组织/账号/角色/权限管理、订单管理、数据报表、配置中心、品类管理和审核效率监督。**上架审核不在此列**——已移交库管（WH）。

## SA-P0-01 组织管理（门店/仓库）
**优先级：** P0
**功能描述：**
管理员维护全平台组织架构（门店/仓库）。门店是回收与核销的现场节点，仓库是设备翻新、审核上架与发货的物流节点。一个仓库可服务多个门店。所有门店/仓库的创建、编辑、关店操作均由系统管理员（SA）执行。

**编码体系：**
| 实体 | 格式 | 示例 |
|------|------|------|
| 门店 | `ST-{州码2位}-{4位序号}` | `ST-MH-0001` |
| 仓库 | `WH-{州码2位}-{4位序号}` | `WH-MH-0001` |
| 平板设备 | `TAB-{门店编码}-{2位序号}` | `TAB-ST-MH-0001-01` |
| 店员 | `STAFF-{门店编码}-{3位序号}` | `STAFF-ST-MH-0001-001` |

印度各邦双字母代码：MH(马哈拉施特拉), DL(德里), KA(卡纳塔克), TN(泰米尔纳德), GJ(古吉拉特), UP(北方邦), WB(西孟加拉), RJ(拉贾斯坦)

**创建门店：**
```
管理员 → "组织管理" → "新建门店"
  → 填写门店信息：
      ├── 门店名称（如 "Dobara - Mumbai Andheri"）
      ├── 所属州/城市（下拉选择，州决定编码前缀）
      ├── 详细地址
      ├── 门店联系电话（公开给C端用户，需验证格式）
      ├── 营业时间（可选）
      ├── GPS 坐标（可选，用于C端同城推荐和门店导航）
      └── 备注
  → 系统自动生成门店编码（如 ST-MH-0001，按州+序号自增）
  → 保存 → 门店状态 = "active"
```
**创建仓库：**
```
管理员 → "组织管理" → "新建仓库"
  → 填写仓库信息：
      ├── 仓库名称（如 "Mumbai Central Warehouse"）
      ├── 所属州/城市
      ├── 详细地址（用于退货收件地址）
      ├── 联系电话
      ├── 服务门店（多选，关联哪些门店）
      └── 备注
  → 系统自动生成仓库编码（如 WH-MH-0001）
```
**门店/仓库列表功能：**
| 功能 | 说明 |
|------|------|
| 搜索筛选 | 按名称、编码、州、状态筛选 |
| 查看详情 | 门店/仓库完整信息 + 关联账号数 + 当前设备数 |
| 编辑门店 | 修改名称、地址、电话、营业时间等 |
| 门店关店 | 状态 active → closed；触发关联账号批量禁用（详见 §九 账号生命周期） |
| 门店重开 | 状态 closed → active；需手动恢复账号 |
**业务规则：**
| 规则项 | 说明 |
|--------|------|
| 门店关店 | 该门店所有 ROLE-CLK/ROLE-OWN 的 user_role_assignment 置 disabled；平板远程登出锁定；待处理设备标记"门店关闭-待转移"；已上架可售设备不受影响（正常售卖） |
| 编码规则 | 门店 `ST-{州码2位}-{4位序号}`、仓库 `WH-{州码2位}-{4位序号}`、店员 `STAFF-{门店编码}-{3位序号}`、平板 `TAB-{门店编码}-{2位序号}` |
| 操作日志 | 所有门店/仓库创建、编辑、关店操作记录审计日志 |

## SA-P0-02 角色与权限管理
**优先级：** P0
**功能描述：**
管理员管理全平台账号、角色与权限。系统采用 RBAC 权限模型，以 6 个预置角色和 23 个原子权限编码为基础，实现精细化的功能访问控制和门店/仓库级数据隔离。所有账号创建、角色分配、权限变更操作均需由系统管理员执行。同一账号可拥有多个角色（每个角色绑定不同的门店/仓库），登录后可在应用内切换角色视图。

**6 个预置角色：**
| 角色编码 | 角色名称 | 所属端 | 绑定实体 | 可删除 |
|------|------|------|------|:---:|
| `ROLE-SA` | 系统管理员 | 内部业务应用（跨端） | 无（全局） | ❌ |
| `ROLE-OWN` | 店老板 | 内部业务应用（跨端） | 门店 | ❌ |
| `ROLE-CLK` | 店员/质检员 | 平板质检工具 | 门店 | ❌ |
| `ROLE-WH` | 库管 | 内部业务应用（跨端） | 仓库 | ❌ |
| `ROLE-DB` | 财务/结算 | 内部业务应用（跨端） | 无（跨门店） | ❌ |
| `ROLE-ENT` | 企业采购员 | C 端 App | 无 | ❌ |

**23 个原子权限编码**（格式 `{resource}:{action}`，完整矩阵见 §2.2 权限与角色映射）：`review:write` 归库管（上架审核操作），`review:read` 归管理员+库管（查看审核历史/效率统计）。

**角色管理功能：**
| 功能 | 说明 |
|------|------|
| 新建自定义角色 | 输入角色名称、描述，勾选该角色可访问的权限编码集合；不可与系统预置角色重名 |
| 编辑角色 | 修改角色名称、描述、权限集合；修改后持有该角色的所有在线账号 JWT 下次刷新时生效（2 小时内） |
| 停用角色 | 不可物理删除系统预置角色或有账号关联的角色；停用后该角色的所有账号失去对应权限 |
| 角色列表 | 展示角色编码、名称、描述、关联账号数、创建时间；可按端筛选 |
| 权限预览 | 选中角色后以表格形式展示该角色在各功能模块的权限明细 |
**账号管理功能——创建账号（三步流程）：**
```
管理员 → "账号管理" → "创建账号"

Step 1: 基本信息
  ├── 输入手机号（10 位印度手机号，登录凭证，全局唯一）
  ├── 输入姓名
  ├── 设置初始密码（或勾选"系统自动生成"→ 8位随机含大小写+数字）
  └── 选择账号类型：内部员工 / 店老板

Step 2: 角色分配
  ├── 选择一个或多个角色
  │     ├── ROLE-OWN → 需进一步选择绑定门店
  │     ├── ROLE-CLK → 需进一步选择绑定门店
  │     ├── ROLE-WH → 需进一步选择绑定仓库
  │     ├── ROLE-DB → 不需绑定组织（跨门店）
  │     └── ROLE-ENT → 不需绑定组织
  └── 每个角色可设置"有效期限"（可选，用于临时工/短期授权）

Step 3: 确认创建
  ├── 预览：手机号、姓名、角色列表、绑定组织、初始密码
  ├── 点击"确认创建"
  └── 系统自动：
        ├── 创建 user 记录（account_status = "pending_activation"）
        ├── 插入 user_role_assignment 记录（每条角色一条记录）
        ├── 若 ROLE-CLK/ROLE-OWN → 自动生成店员编号（STAFF-{门店编码}-{序号}）
        └── 发送邀请 SMS（含临时密码 + App 下载链接 + 门店名称）
```
**邀请 SMS 模板：**
```
[Platform] You've been added as [角色名] at [门店/仓库名].
Login: your phone number
Temp Password: XXXXXXXX
Download: [App Store / Play Store 短链]
Change your password after first login.
---
आपको [门店名] में [角色名] के रूप में जोड़ा गया है।
लॉगिन: आपका फ़ोन नंबर | पासवर्ड: XXXXXXXX
ऐप: [短链] | पहले लॉगिन के बाद पासवर्ड बदलें।
```
**账号列表与操作：**
| 功能 | 说明 |
|------|------|
| 创建账号 | 三步流程（基本信息 → 角色分配 → 确认创建），系统自动发送邀请 SMS |
| 编辑账号 | 修改姓名、角色分配、门店/仓库绑定、启用/禁用状态 |
| 禁用账号 | 禁用后该账号即时无法登录，5 分钟内当前会话自动登出，历史数据保留 |
| 重新启用 | 状态 disabled → active，原角色和权限不变 |
| 账号列表 | 按端/角色/门店/仓库/状态筛选，展示：用户ID、姓名、手机号(脱敏)、角色、绑定组织、状态标签、最近登录时间 |
| 重置密码 | 生成新临时密码 → 发送 SMS → 用户下次登录需重新激活（设新密码+同意协议） |
| 更换手机号 | 输入新手机号 → OTP 验证 → 更新 phone → 新旧手机号同时收到通知 SMS |
| 强制踢出 | 该账号所有设备的 JWT 立即失效（加入黑名单），正在使用的会话强制登出 |
| 查看详情 | 完整账号信息 + 角色分配历史 + 登录历史 + 操作审计 |
**账号状态标签：**
| 状态 | 标签颜色 | 说明 |
|------|:---:|------|
| `pending_activation` | 橙色 | 待激活（收到邀请但未登录），7 天后自动清理 |
| `active` | 绿色 | 正常使用中 |
| `locked` | 红色 | 密码错误 5 次临时锁定（15 分钟） |
| `disabled` | 灰色 | 管理员已禁用 |
| `removed` | 灰色 | 已被移除（不可逆终态） |
| `deleted` | 灰色 | 用户已注销（终态） |
**激活流程适用范围：**
| 角色 | 创建人 | 是否走激活流程 | 说明 |
|------|------|:---:|------|
| ROLE-OWN（店老板） | SA | ✅ 是 | SA 创建后发送邀请 SMS → 店老板首次登录强制激活（设新密码+同意协议） |
| ROLE-CLK（店员） | SA 或 OWN | ✅ 是 | 创建后发送邀请 SMS → 店员首次登录强制激活 |
| ROLE-WH（库管） | SA | ✅ 是 | 创建后发送邀请 SMS → 库管首次登录强制激活 |
| ROLE-DB（财务） | SA | ❌ 否 | 内部员工，SA 创建后直接设为 active |
| ROLE-ENT（企业采购员） | SA | ❌ 否 | 企业客户，SA 创建后直接设为 active |
| ROLE-SA（系统管理员） | 初始化脚本 | ❌ 否 | 系统部署时直接创建，初始密码需在首次登录后修改 |
> **规则：** 需要绑定门店/仓库的外部角色（OWN/CLK/WH）走激活流程；不绑定组织的内部角色（DB/ENT/SA）直接激活。
**特殊情况——已有平台账号：**
若被邀请的手机号已是平台用户（如该用户已在其他门店做过店员，或已有 C 端账号），则：
- 不创建新 user 记录，直接在 `user_role_assignment` 表新增角色绑定
- 状态直接设为 `active`（免激活）
- 发送通知 SMS："你已被添加为 [门店名] 的 [角色名]，请登录 App 查看"
**未激活账号清理规则：**
| 维度 | 说明 |
|------|------|
| 清理时机 | 创建后 **7 天**未激活 → 系统定时任务自动清理（每日凌晨执行） |
| 清理范围 | 删除 `user` 记录 + 关联的 `user_role_assignment` 记录（仅清理 pending_activation 且无其他 active 角色的 user） |
| 数据保留 | **清理后不留存**——该账号无任何业务数据（未登录=无操作记录），无需保留 |
| 多角色保护 | 若该手机号已有其他已激活角色（如同时被分配了 OWN 和 CLK，已激活 OWN 但 CLK 待激活），则仅删除该 pending 的 role_assignment 记录，不删除 user |
| 再次创建 | 清理后**可再次使用同一手机号创建账号**——手机号从 user 表移除后即释放，SA/OWN 可重新发起邀请 |
**`removed` 状态详细说明：**
| 维度 | 说明 |
|------|------|
| 触发人 | OWN（店老板移除本门店店员）或 SA（系统管理员移除任意账号角色） |
| 触发场景 | 店员离职、店老板变更、角色分配错误需撤销、门店关店批量移除 |
| 即时效果 | 移除后该账号**即时**无法登录平板/App；当前在线会话 5 分钟内强制登出 |
| 数据保留 | 该店员的历史质检记录、操作日志**完整保留**在原门店，操作人信息不变 |
| 可逆性 | **不可逆**——一旦移除不可恢复。如需重新授权，须走完整创建流程（邀请→激活） |
| 多角色场景 | 仅移除被选中的角色绑定（如移除 CLK 角色），不影响该账号的 OWN/WH 等其他角色 |
| 与 `disabled` 区别 | `disabled` 可重新启用（reversible），`removed` 不可恢复（terminal） |
| 与 `deleted` 区别 | `deleted` 是用户主动注销（30 天冷静期），`removed` 是管理员操作（立即生效） |
**多角色切换：**
| 场景 | 说明 |
|------|------|
| 同一账号多角色 | 如某员工同时持有 ROLE-OWN + ROLE-DB，登录后切换角色视图 |
| 切换行为 | 切换角色后生成新 JWT（含目标角色的权限声明），刷新界面 |
| 权限计算 | 每个角色独立 JWT；当前 token 的 permissions = 该角色的权限集合 |
| 真实案例 | 一家门店的老板可能也是该区域多家门店的 DB——OWN(ST-MH-0001)+DB(null) |
**门店/仓库数据隔离：**
| 规则项 | 说明 |
|--------|------|
| 门店隔离 | ROLE-OWN 和 ROLE-CLK 通过 JWT 中的 org_id=ST-MH-0001 实现数据隔离，只能访问本门店数据 |
| 仓库隔离 | ROLE-WH 通过 JWT 中的 org_id=WH-MH-0001 实现数据隔离，只能操作本仓库 |
| DB 跨门店 | ROLE-DB 的 org_id=NULL，可跨门店查看结算和营收数据，但无写权限 |
| 跨门店授权 | 区域经理等特殊情况可创建自定义角色，授予多门店/多仓库的 inspection:read 权限 |
| 数据范围变更 | SA 修改账号的 org_id 绑定后，用户下次切换角色或重新登录时生效 |
| 平板设备 | 平板安装 App 即可使用，无需注册；店员登录后门店上下文从店员所属门店解析；平板丢失/报废无需后台操作 |
**业务规则：**
| 规则项 | 说明 |
|--------|------|
| 权限粒度 | 按 23 个原子权限编码控制；自定义角色可任意组合权限编码 |
| 权限变更生效 | 角色权限修改后，持有该角色的在线用户需刷新 JWT（2 小时内自动刷新） |
| 默认角色 | 系统预置 6 个角色（SA/OWN/CLK/WH/DB/ENT），不可删除，可修改权限配置 |
| 管理员保护 | ROLE-SA 由系统初始化脚本创建，不可被其他管理员禁用或删除 |
| 店员上限 | 默认每个门店最多 10 个 ROLE-CLK 店员，管理员可配置 |
| 邀请过期 | 创建账号后 7 天内未激活 → 自动清理（user 和 user_role_assignment 记录删除） |
| 操作日志 | 所有角色创建/修改、账号创建/禁用/权限变更操作记录审计日志 |
**验收标准：**
- [ ] 管理员可创建门店和仓库，编码自动按州+序号生成
- [ ] 管理员可通过三步流程创建账号：基本信息 → 角色分配 → 确认创建，系统自动发送邀请 SMS
- [ ] 账号创建后关联角色和绑定组织的 user_role_assignment 记录正确
- [ ] 管理员可创建/编辑/停用角色，每个角色可勾选 23 个原子权限编码
- [ ] 管理员可编辑/禁用/重新启用/强制踢出/重置密码/更换手机号等全套账号操作
- [ ] 同一账号多角色时，每个角色绑定独立的门店/仓库，应用内切换角色后权限正确
- [ ] ROLE-OWN 仅可查看本门店数据，不可跨门店访问
- [ ] ROLE-WH 仅可查看本仓库数据，不可跨仓库访问
- [ ] ROLE-DB 可跨门店查看结算数据但不可操作质检/核销/店员管理
- [ ] 角色权限变更后在线用户 2 小时内自动刷新权限
- [ ] 账号禁用后即时无法登录，5 分钟内当前会话自动登出
- [ ] 系统预置 6 个默认角色不可删除
- [ ] 7 天未激活的待激活账号自动清理
- [ ] 门店关店触发关联账号批量禁用和平板远程锁定
- [ ] 所有权限管理操作记录审计日志

## SA-P0-03 回收订单管理
**优先级：** P0
**功能描述：**
管理员查看全平台所有回收订单，支持按门店、状态、时间范围等维度筛选和搜索。回收订单记录从用户到店质检到核销完成的完整链路，是平台的**核心业务流水**。管理员通过此模块进行客服排查、异常处理和数据核对。
**回收订单列表字段：**
| 字段 | 说明 | 示例 |
|------|------|------|
| 订单编号 | 系统自动生成，格式 `RO-{YYYYMMDD}-{6位序号}` | `RO-20260810-000123` |
| 用户手机号 | 中间 4 位脱敏 | `+9198****210` |
| 设备信息 | 品牌 + 型号 + 存储 + IMEI 后四位 | `iPhone 12 · 128GB · ****1234` |
| 回收门店 | 门店名称 + 编码 | `Dobara - Mumbai Andheri (ST-MH-0001)` |
| 质检等级 | 系统判定 / 审核调整后的最终等级 | A / B / C / D（彩色标签） |
| 回收价 | 最终成交回收价（INR） | `₹18,500` |
| 新机售价 | 店老板录入的新机售价（如有换购） | `₹54,900` |
| 抵扣金额 | 回收价直接抵扣新机的金额 | `₹18,500` |

## SA-P0-05 配置中心
**优先级：** P0
**功能描述：**
管理员集中管理平台所有可动态调整的业务参数、选项列表和规则阈值。配置中心将每个可调项暴露为可视化表单控件（开关/数字输入/下拉/列表编辑），变更后即时生效或按规则生效，无需发版或重启服务。所有配置变更记录操作日志。配置中心按业务域分为 7 个配置组，SA 和具有 `pricing:config` 权限的角色可操作。

**设计原则：**
| 原则 | 说明 |
|------|------|
| 零代码变更 | 所有可调参数均通过后台 UI 修改，不通过代码常量或配置文件 |
| 即时生效 | 修改保存后推送到 Redis，服务端实时读取最新值；部分参数（如JWT时长）需下一次签发时生效 |
| 变更审计 | 每次修改记录：操作人、时间、配置项key、旧值→新值、变更原因（可选） |
| 版本回滚 | 每项配置保留最近 10 次历史值，支持一键回滚到任意历史版本 |
| 默认值保护 | 所有配置项有系统默认值；管理员修改过的项标记"已自定义"；支持恢复默认 |
| 全局 vs 门店级 | 大部分参数为全局配置；标注"门店级"的可按门店独立设置（如店员上限） |

## SA-P1-01 审核历史与效率统计
**优先级：** P1
**功能描述：**
管理员查看全平台的审核历史查询和库管审核效率统计（对应"管理员看行为数据"定位）。管理员可按时间范围、门店、审核人维度筛选历史审核记录，查看每台设备的审核详情（审核人、审核时间、审核结果、调整项）。效率统计按审核人汇总人均审核量和平均审核时效，支持数据导出，用于审核团队绩效考核和工作量管理。**管理员本身不操作审核，但监督库管的审核质量与时效。**
**审核历史查询：**
| 筛选项 | 说明 |
|--------|------|
| 时间范围 | 日期选择器，支持快捷选择（今日/昨日/本周/本月/自定义） |
| 审核人 | 下拉多选，列出所有库管（具备审核权限） |
| 审核结果 | 下拉单选：全部 / 直接上架 / 调整后上架 |
| 门店 | 下拉多选，按门店筛选设备来源 |
| 品牌/机型 | 下拉筛选，级联选择 |
| 成色等级 | 多选 A/B/C/D |
**审核历史列表字段：**
| 字段 | 说明 |
|------|------|
| 设备标识 | 品牌 + 型号 + IMEI 后四位 |
| 来源门店 | 回收门店名称 |
| 原成色等级 | 系统判定或店员评定的原始等级 |
| 审核后成色等级 | 审核后的最终等级（调整时展示变化箭头） |
| 审核结果 | 直接上架 / 调整后上架（标签展示） |
| 回收价变化 | 原回收价 → 调整后回收价（仅调整时展示） |
| 审核人 | 审核操作人员姓名 |
| 审核时间 | 审核提交时间 |
| 操作 | 查看审核详情（展开审核工作台回放，含影像、扣款明细、调整原因） |
**审核效率统计：**
| 统计指标 | 说明 |
|----------|------|
| 人均日审核量 | 按天统计每个审核人的审核设备数量 |
| 人均周/月审核量 | 按周/月聚合统计 |
| 平均单台审核耗时 | 从打开审核工作台到点击提交的时间差 |
| 直接上架率 | 直接上架数 / 总审核数（机况一致性指标，可间接反映门店质检质量） |
| 调整率 | 调整后上架数 / 总审核数 |
| 常见调整项分布 | 统计各扣款项被库管补勾的频次（如"屏幕划痕"被补勾 120 次），用于优化平板外观点检引导 |
| 各门店调整率排名 | 按门店统计其设备被审核调整的比例，识别质检质量薄弱的门店 |
**统计展示形式：**
| 展示形式 | 适用场景 |
|----------|----------|
| 汇总卡片 | 总审核量、今日审核量、平均审核耗时等核心 KPI |
| 折线图 | 审核量趋势（按天/周/月） |
| 柱状图 | 各审核人审核量对比、各门店调整率对比 |
| 饼图 | 审核结果分布（直接上架 vs 调整后上架） |
| 数据表格 | 详细审核记录列表，支持排序和导出 |
**数据导出：**
| 导出类型 | 说明 |
|----------|------|
| 审核历史明细 | 导出当前筛选条件下的审核记录为 Excel/CSV |
| 效率统计报表 | 导出按审核人/时间段聚合的统计报表为 Excel |

## OWN-P0-02 店员管理
**优先级：** P0
**功能描述：**
店老板在 App 内管理本门店的店员账号（仅限 ROLE-CLK 质检店员），包括添加店员、移除店员、查看店员列表。店员账号用于平板质检工具的登录和操作。添加店员时采用邀请制——店老板输入店员手机号后系统发送邀请 SMS，店员通过邀请链接下载 App 并激活账号。

**添加店员流程：**

```
店老板登录 → "店员管理" → 点击"添加店员"
  → 输入店员手机号（10 位印度手机号，以 6/7/8/9 开头）
  → 店员角色固定为 ROLE-CLK（质检店员），不可选择其他角色
  → 点击"发送邀请"

服务端校验：
  ├── 该手机号是否已是本门店店员？→ 是 → 提示"该员工已在本门店"
  ├── 店员数量是否达上限？→ 是（默认 10 人/店）→ 提示"店员数量已达上限，请联系管理员"
  └── 全部通过 →
        ├── 若该手机号已有平台账号：
        │     → 在 user_role_assignment 表中新增记录
        │     → 状态 = "active"（直接激活，无需激活流程）
        │     → 发送通知 SMS
        └── 若该手机号无平台账号：
              → 创建 user 记录
              → 生成临时密码（8 位随机，含大小写+数字）
              → 在 user_role_assignment 表中新增记录
              → 状态 = "pending_activation"
              → 发送邀请 SMS（含临时密码 + App 下载链接）
              → 店员首次用临时密码登录 → 强制激活流程（同 UA-P0-01）
```

| 店员正在质检中（平板在线 + 有进行中的 inspection session） | 移除操作不阻断；移除生效后：平板端 5 分钟内强制登出；进行中的质检 session 自动标记为"已中断-操作人被移除"，已上传的图片/数据不丢失；提示店老板"该店员有 1 个进行中的质检任务，移除后将自动中断" |
| 移除待激活（pending）状态的店员 | 直接移除，无需 5 分钟登出等待（从未登录过）；邀请 SMS 中的临时密码即时失效；该店员手机号可被其他门店立即添加 |
| 店老板尝试移除自己 | 禁止操作；提示"店老板不可移除自己。如需注销账号，请前往设置 → 注销账号" |
| 移除最后一个店员（门店店员数将变为 0） | 允许移除，但二次确认强化提示："移除后本门店将无店员，平板质检将无法执行。确定移除吗？" |
| 移除操作提交时网络中断 | 服务端幂等：同一店员在同一门店的 user_role_assignment 状态已是 removed，重复提交返回"该店员已被移除"；App 端乐观更新：确认后立即从列表移除，网络恢复后同步校验 |
| 被移除店员属于多个门店 | 仅撤销当前门店的 user_role_assignment，其他门店角色不受影响；该店员仍可用同一手机号登录，但在当前门店视图中不展示 |
| 移除后立即重新添加同一店员 | 允许；添加时该店员重新进入 pending 状态（若之前已激活则直接 active）；原历史质检记录不受影响，在同一个 staff_id 下恢复关联；无冷却期限制 |
| 移除操作后通知被移除店员 | 向被移除店员手机号发送 SMS："[Platform] 您在 [门店名称] 的质检店员身份已被移除。如有疑问请联系店老板。"；被移除店员下次尝试登录平板时展示"您已被移除出该门店"页面 |
| 移除时店员账号处于"已禁用"或"已锁定"状态 | 允许移除；移除后 user_role_assignment 状态变更为 removed，该状态独立于账号级别的 disabled/locked |
| SA 在管理员视图移除店员 vs 店老板在 App 移除 | 两种路径均可，效果一致；SA 移除时需填写操作原因（必填），审计日志区分操作来源 |

**验收标准：**

- [ ] 添加店员时不可选择库管角色（ROLE-WH）

### KPI 指标定义与计算规则

**1. 回收量**

| 维度 | 说明 |
|------|------|
| 定义 | 用户接受报价并完成核销的旧机台数 |
| 计算公式 | `COUNT(device WHERE status >= '已核销' AND store_id = 当前门店 AND redemption_date IN 时间范围)` |
| 数据来源 | device 表，status 字段 |
| 环比 | （本期 - 上期）/ 上期 × 100%；上升绿色 ↑、下降红色 ↓ |
| 粒度 | 日 / 周 / 月，默认"本月" |

**2. 总抵扣金额**

| 维度 | 说明 |
|------|------|
| 定义 | 所有核销完成的旧机抵扣金额合计 |
| 计算公式 | `SUM(price_trade_in WHERE device.store_id = 当前门店 AND status >= '已核销' AND redemption_date IN 时间范围)` |
| 单位 | INR 卢比，千分位格式化（如 ₹8,20,500），缩写为 ₹8.2L |
| 环比 | 同上 |
| 注意 | 此为旧机抵扣金额，非门店收入；抵扣金额越高意味着给用户的优惠越多 |

**3. 换购成交笔数**

| 维度 | 说明 |
|------|------|
| 定义 | 用户完成核销确认的换购交易笔数（用户点击"确认核销"） |
| 计算公式 | `COUNT(redemption WHERE store_id = 当前门店 AND status = 'confirmed' AND confirmed_at IN 时间范围)` |
| 与回收量的关系 | 回收量 ≈ 换购成交笔数；差异场景：用户接受报价但放弃买新机（计入回收量不计入换购成交，P1 后续追踪） |
| 环比 | 同上 |

**4. 审核调整率**

| 维度 | 说明 |
|------|------|
| 定义 | 回收设备中被审核调整的比例（成色/扣款/价格任一变动即计入） |
| 计算公式 | `COUNT(device WHERE review_adjusted = true AND store_id = 当前门店 AND audited_at IN 时间范围) / COUNT(device WHERE store_id = 当前门店 AND audited_at IN 时间范围) × 100%` |
| 单位 | 百分比，保留 1 位小数 |
| 环比 | 上升红色 ↑（越高质量越差）、下降绿色 ↓ |
| 业务含义 | 反映门店质检质量；调整率越高说明店员质检不够准确，需要培训 |

**5. 回收转化率**

| 维度 | 说明 |
|------|------|
| 定义 | 用户接受报价的比例 |
| 计算公式 | `COUNT(device WHERE user_accepted = true AND store_id = 当前门店 AND quoted_at IN 时间范围) / COUNT(device WHERE store_id = 当前门店 AND quoted_at IN 时间范围) × 100%` |
| 单位 | 百分比，保留 1 位小数 |
| 业务含义 | 报价是否合理；转化率低可能意味着报价偏低或用户期望值过高 |

**6. 平均抵扣金额**

| 维度 | 说明 |
|------|------|
| 定义 | 已核销设备的平均旧机抵扣金额 |
| 计算公式 | `AVG(price_trade_in WHERE device.store_id = 当前门店 AND status >= '已核销' AND redemption_date IN 时间范围)` |
| 单位 | INR 卢比，千分位格式化 |
| 业务含义 | 反映回收设备的平均价值水平 |

**7. 本月新机销售额**

| 维度 | 说明 |
|------|------|
| 定义 | 换购交易中新机售价合计 |
| 计算公式 | `SUM(new_device_price WHERE store_id = 当前门店 AND redemption.status = 'confirmed' AND confirmed_at IN 时间范围)` |
| 单位 | INR 卢比，千分位格式化 |
| 业务含义 | 门店通过换购带动的新机销售收入 |

## 六、库管角色模块（原 WH）

> 库管（ROLE-WH）账号由 SA 在内部业务应用创建和管理，绑定至指定仓库。库管登录后进入 WH 视图，操作本仓库的设备流转（入库/翻新/出库），并在审核工作台完成上架审核。

## WH-P0-01 设备入库确认
**优先级：** P0
**功能描述：**
核销完成后，旧机由门店发至仓库。库管接收实物后，在 App 中扫描设备包装上的条码完成入库确认。系统自动关联门店质检环节已上传的影像和硬件数据，无需库管重复采集。

**入库流程：**

```
库管登录 → WH 视图首页 → 点击"入库扫码"
  → 摄像头扫描设备包装条码（IMEI 或 session_id）
  → 系统查询设备信息：
      ├── 设备不存在？→ 提示"未找到该设备，请确认条码正确"
      ├── 设备状态 ≠ "待入库"？→ 提示"该设备当前状态为 [X]，不可入库" + 展示当前状态说明
      ├── 设备绑定仓库 ≠ 当前仓库？→ 提示"该设备属于 [仓库名称]，请发往正确仓库"
      └── 校验通过 →
            → 展示设备确认卡：
              ┌──────────────────────────────────┐
              │  设备入库确认                      │
              │  IMEI: 356303489012***            │
              │  品牌型号: Apple iPhone 13        │
              │  成色: B（系统判定）                │
              │  存储: 128GB                      │
              │  来源门店: ST-MH-0001              │
              │  质检员: STAFF-ST-MH-0001-003      │
              │                                  │
              │  [查看质检影像]  [查看硬件报告]     │
              │                                  │
              │  [ 确认入库 ]  [ 标记异常 ]        │
              └──────────────────────────────────┘
            → 点击"确认入库" →
                ├── device.status → "在库可售"（无需翻新）/ "待翻新"（需翻新判断）
                ├── device.warehouse_id → 当前仓库 ID
                ├── 入库时间 → now()
                ├── 入库操作人 → 当前库管 ID
                └── 设备进入本仓库的审核队列，等待库管审核
```

**标记异常：**

```
库管发现设备实物与质检报告不符（如成色明显偏差、配件缺失、IMEI 不匹配）
  → 点击"标记异常" → 选择异常原因：
      ├── 成色与报告不符（拍照上传实物照片）
      ├── 配件缺失（勾选缺失项：充电器/数据线/包装盒/耳机）
      ├── IMEI 标签与实物不一致
      ├── 设备有明显运输损坏（拍照）
      └── 其他（手动填写）
  → 提交 → 设备状态 → "入库异常"
  → 通知管理员 → 管理员介入处理
```

**业务规则：**

| 规则项 | 说明 |
|--------|------|
| 扫码方式 | 摄像头扫描条码（支持 Code 128/QR Code）或手动输入 IMEI |
| 扫码响应 | 扫码后 2 秒内展示设备确认卡 |
| 入库校验 | 校验设备状态为"待入库"（即核销已完成 + 未入库）；状态不符时展示当前状态并阻止入库 |
| 仓库校验 | 校验设备绑定的目标仓库与当前库管所属仓库一致；不一致时提示正确仓库名称 |
| 影像复用 | 入库时自动关联门店质检环节的影像和硬件检测数据，无需库管重新拍摄 |
| 批量入库 | 支持连续扫码（入库完一台自动回到扫码页），无需手动返回 |
| 入库后状态 | 设备状态变更为"在库可售"；进入审核队列，等待库管审核后上架 |
| 异常标记 | 标记异常后设备进入"入库异常"状态，通知管理员；库管不可自行修改设备信息 |
| 入库统计 | 首页展示今日入库台数 + 待入库台数角标 |

**异常场景：**

| 场景 | 处理方案 |
|------|----------|
| 扫码后设备不存在 | 提示"未找到该设备"；支持手动输入 IMEI 重试；连续 3 次失败建议检查实物 |
| 同一设备重复扫码入库 | 提示"该设备已入库（入库时间：YYYY-MM-DD HH:MM，操作人：[姓名]）"；不重复创建入库记录 |
| 设备绑定仓库与当前仓库不匹配 | 提示"该设备应发往 [正确仓库名称]"；不记录入库；该设备不会出现在当前仓库的待入库列表 |
| 扫码时网络中断 | 扫码结果本地缓存（最近 50 条）；恢复网络后自动提交；本地缓存与服务器去重 |
| 设备在途但库管误操作入库 | 物理未到但条码已扫 → 仍记录入库；由后续实物核对（盘点）发现差异 |

**验收标准：**
- [ ] 扫码后 2 秒内展示设备确认卡，信息完整
- [ ] 入库后设备状态正确变更为"在库可售"
- [ ] 状态不符时明确提示不可入库原因和当前状态
- [ ] 仓库不匹配时提示正确仓库名称
- [ ] 可查看关联的质检影像和硬件报告
- [ ] 标记异常后设备进入"入库异常"状态，管理员收到通知
- [ ] 连续扫码模式可用，入库完成自动回到扫码页
- [ ] 首页展示今日入库台数和待入库角标

## WH-P0-00 仓库翻新质检
**优先级：** P0
**功能描述：**
设备入库后，库管判断是否需要翻新。翻新质检是对门店质检的补充和修正——仓库具备更专业的检测条件和拆机能力，可发现门店平板检测不到的深层问题。翻新质检完成后，系统以翻新数据覆盖门店质检数据，重新计算成色与回收价。

**翻新判断流程：**

```
入库完成 → 自动弹出翻新判断（或从设备详情进入）
  → 库管目视初检：
      ├── 外观无可见问题，门店质检数据可信 → "无需翻新" → 设备直接进入"在库可售"
      └── 存在以下任一情况 → 进入翻新质检：
            ├── 外观评级可能有偏差（拍照与实际不符）
            ├── 硬件检测数据存疑（如电池健康度与机型年代不匹配）
            ├── 屏幕/后盖更换痕迹（非原厂部件）
            ├── 进水指示器有轻微变色（未触发门店拒收但需进一步检查）
            └── 用户反映设备有隐性故障（间歇性重启/信号差等）
```

**翻新质检内容：**

```
翻新质检流程（与门店质检类似，但更深入）：

1. 外观复检（覆盖门店数据）
   ├── 10 张标准角度照片（使用 App 自带相机，仓库光照条件更好）
   ├── 外观点检（重新逐项判定，以仓库结果为准）
   ├── 重点拍摄：门店照可能遗漏的边角/缝隙
   └── 成色等级以翻新结果重新判定

2. 硬件深度检测（覆盖门店数据）
   ├── 屏幕：触摸全屏划线测试 + 坏点全屏纯色测试 + 3D Touch（如有）
   ├── 电池：重新读取健康度 + 充电循环次数 + 是否原厂电池
   ├── 摄像头：前后摄拍照 + 闪光灯 + 对焦测试 + 防抖
   ├── 按键：音量± + 静音键 + 电源键（各按 5 次感应）
   ├── 生物识别：Face ID / Touch ID 功能测试
   ├── 音频：听筒 + 底部扬声器 + 麦克风（录音回放）
   ├── 传感器：距离传感器 + 光线传感器 + 陀螺仪 + 指南针 + 气压计
   ├── 震动马达：震动强度测试
   ├── 无线：WiFi 连接 + 蓝牙配对 + GPS 搜星
   ├── 通话：SIM 卡插入测试通话质量 + 听筒清晰度
   └── 拆机检查（如有工具）：
         ├── 主板完整性（无维修痕迹/飞线/腐蚀）
         ├── 内部螺丝完整（无缺失/滑丝）
         ├── 防水标完整状态
         └── 电池是否为原厂（核对序列号）

3. 配件完整性检查
   ├── SIM 卡托：有无 + 是否匹配 IMEI
   ├── 原厂充电器/数据线：有无 + 是否原厂
   └── 包装盒：有无 + 成色

4. 数据上传 → 覆盖门店质检数据 → 定价引擎重新计算
   ├── 新回收价（可能低于门店报价）
   ├── 新成色等级
   ├── 新商城售价
   └── 翻新前后价格差异 > 15% 时 → 标记"重大差异"，通知管理员关注
```

**翻新后定价：**

| 场景 | 处理 |
|------|------|
| 翻新后回收价与门店价差异 ≤ 5% | 以翻新价为准，自动进入"在库可售" |
| 翻新后回收价与门店价差异 5%-15% | 以翻新价为准，标记"价格变动"，审核时展示差异 |
| 翻新后回收价与门店价差异 > 15% | 以翻新价为准，标记"重大差异"；审核时红色高亮，建议重点审核 |
| 翻新后发现不可逆缺陷（如主板维修痕迹） | 标记"不可售-拆件"，进入拆件库存（P2 拆件功能） |

**业务规则：**

| 规则项 | 说明 |
|--------|------|
| 翻新触发 | 入库后库管手动判断；不可跳过（必须执行"需要翻新"或"直接通过"二选一） |
| 数据覆盖 | 翻新质检数据上传后完全覆盖门店质检数据（硬件检测 + 外观评级 + 影像）；门店数据保留在历史版本中 |
| 定价重算 | 翻新后系统自动触发定价引擎重新计算回收价 + 商城售价；使用与门店定价相同的公式 |
| 翻新历史 | 每次翻新质检创建新版本记录（version 1 = 门店质检, version 2 = 第一次翻新, ...），可追溯对比 |
| 成色重新判定 | 以翻新点检结果重新走逐级熔断规则，不以门店定级为基础 |
| 不可翻新 | 已标记为"拒收"或"已完成-拒收"的设备不进入翻新流程 |
| 操作人记录 | 翻新质检操作人记录为当前库管 ID，与门店质检员区分 |

**验收标准：**
- [ ] 入库后强制弹出翻新判断（二选一），不可跳过
- [ ] "直接通过"后设备进入"在库可售"
- [ ] 翻新质检覆盖外观复检（10 张照 + 点检）+ 硬件深度检测 + 配件检查
- [ ] 翻新数据上传后覆盖门店数据，设备历史版本可追溯
- [ ] 翻新后系统自动重算回收价 + 商城售价
- [ ] 价格差异 > 15% 时自动标记"重大差异"，审核界面红色高亮
- [ ] 翻新前后数据差异在设备详情页可对比查看（版本对比）
- [ ] 发现不可逆缺陷时设备标记"不可售-拆件"

## WH-P0-06 上架审核
**优先级：** P0
**功能描述：**
库管对本仓库的待上架设备进行审核。审核时对比质检影像与系统判定的扣款项是否一致。若一致则直接上架；若不一致，库管补勾店员遗漏的扣款项（外观缺陷/硬件扣款），提交后系统自动重新判定成色等级并计算回收价和商城售价，然后上架。不设"拒绝上架"操作——所有设备均会上架。**库管不手动调整成色等级，等级完全由系统根据扣款项通过逐级熔断规则自动判定。**
**审核流程：**
```
待上架设备进入本仓库审核队列
  → 库管打开审核工作台
    → 查看设备外观影像（10 张照片 + 1 段视频）+ 硬件检测摘要 + 当前成色等级 + 扣款明细
    → 判断机况是否与系统判定一致
      ├── 机况一致 → 点击"直接上架"
      │     → 上传商品主图（必填）
      │     → 设备状态 → [在库可售]
      │
      └── 机况不符 → 点击"调整后上架"展开调整面板
            → 补勾店员遗漏的扣款项（外观 / 硬件）
            → 填写调整原因（必填，≥10 字）
            → 提交后系统自动重新判定成色等级（逐级熔断）
            → 系统重新计算回收价 + 商城售价
            → 上传商品主图（必填）
            → 推送调整详情至对应门店平板
            → 设备状态 → [在库可售]
```
**审核界面要素：**
| 区域 | 内容 |
|------|------|
| 任务队列 | 按入库时间排序的本仓库待审核设备列表，支持按品牌/机型/成色等级筛选 |
| 审核工作台-左侧 | 10 张外观照片可切换查看 + 视频播放器（支持暂停/拖动/全屏） |
| 审核工作台-右侧 | 硬件检测摘要 + 当前成色等级 + 扣款明细（逐项列出） |
| 商品主图上传 | 库管从系统图片库选择（图片库由管理员在 SA-P2-02 品类管理维护的精修图）或本地上传，支持预览裁剪 |
| 操作区 | "直接上架"（机况一致）+ "调整后上架"（机况不符） |
**审核任务队列字段：** 设备标识（品牌+型号+IMEI 后四位）、存储/颜色、来源门店、店员、入库时间、当前成色等级、系统回收价、待审时长（超 24h 橙色）、操作。
**审核任务队列筛选：** 品牌、机型（级联）、成色等级、来源门店、入库时间、待审时长（24h 内/已超时）。
**业务规则：**
| 规则项 | 说明 |
|--------|------|
| 仓库隔离 | 库管仅审核本仓库（org_id=WH-xxx）的待上架设备，不可跨仓审核 |
| 跨仓兜底 | 管理员可在审核队列页看到全平台按仓库聚合的待审池，可手动将某仓库待审设备指派给任意库管（跨仓指派）；无库管且未指派的设备在"无审核人"告警中高亮 |

| 等级由系统判定 | 库管不手动调整成色等级；等级由定价引擎按逐级熔断规则自动判定 |
| 调整原因必填 | "调整后上架"时调整原因必填，≥10 字符 |
| 商品主图必填 | 直接上架/调整后上架均需上传至少一张商品主图 |
| 不可回退 | 上架操作一旦提交不可撤回 |
| 审核时效 | 入库后超 24h 未审核标记"超时待审"橙色提醒 |
| 调整日志 | 记录操作人、时间、调整前后对比（扣款+等级+价格）、原因 |
**验收标准：**

## WH-P0-03 扫码核销 IMEI
**优先级：** P0
**功能描述：**
库管从货架取到设备后，扫描设备 IMEI 条码进行出库核销。系统实时校验 IMEI 与出库任务中的设备匹配，防止错发。核销是出库的最终确认动作——核销后设备状态变更为"已出库"，库存扣减，订单状态同步更新。

**核销流程：**

```
出库任务详情页 → 点击"扫码出库核销"
  → 打开摄像头 → 扫描设备机身/包装上的 IMEI 条码
  → （也支持手动输入完整 IMEI 作为兜底）
  → 系统校验：
      ├── IMEI 是否存在于系统？→ 否 → 提示"未找到该 IMEI，请确认"
      ├── IMEI 是否属于当前出库任务？→ 否 →
      │     ├── IMEI 属于同一仓库的其他出库任务？
      │     │     → 提示"该设备属于订单 [ORD-xxx]，非当前出库任务。
      │     │        点击跳转至正确任务？"
      │     └── IMEI 不属于任何出库任务？
      │           → 告警"该设备无待出库任务，不可出库" + 阻止操作
      ├── IMEI 是否已出库？→ 是 → 提示"该设备已于 YYYY-MM-DD HH:MM 出库（操作人：[姓名]）"
      └── 全部通过 →
            → 展示核销确认卡：
              ┌──────────────────────────────────┐
              │  出库核销确认                      │
              │                                  │
              │  设备：iPhone 13 128GB 蓝色        │
              │  IMEI：3563034890123456           │
              │  成色：B                           │
              │  订单：ORD-20260811-0012 (B2C)    │
              │  收件人：Rahul Sharma              │
              │  地址：Mumbai, Maharashtra 400001  │
              │  物流：Delhivery                   │
              │                                  │
              │  ⚠ 请确认实物 IMEI 与以上信息一致   │
              │                                  │
              │  [ 确认出库核销 ]  [ 取消 ]        │
              └──────────────────────────────────┘
            → 点击"确认出库核销" → 二次确认弹窗：
                "确认核销后设备状态将变更为'已出库'，此操作不可撤销。确定？"
            → 确认 →
                ├── device.status → "已出库"（终态）
                ├── 订单状态 → "已发货"
                ├── 库存数量 -1
                ├── 出库时间 → now()
                ├── 出库操作人 → 当前库管 ID
                ├── 触发面单打印（如已配置自动打印）
                └── 向用户/企业发送发货通知 SMS
```

**业务规则：**

| 规则项 | 说明 |
|--------|------|
| 一设备一任务 | 每台设备同一时间只属于一个出库任务；不可一机多出 |
| IMEI 精确匹配 | 必须 15 位 IMEI 完全匹配；不支持模糊匹配 |
| 二次确认 | 核销需二次确认 + 展示不可撤销提示 |
| 核销后不可撤销 | 出库核销为终态操作；如需撤销需联系 SA 后台处理（标记"异常撤销"） |
| 连续核销 | B2B 批量订单支持连续扫码核销（核销完一台自动回到扫码页，展示剩余台数） |
| 手动输入兜底 | 条码损坏无法扫描时可手动输入 IMEI；手动输入时需二次确认"条码不可读，确认手动输入？" |

**异常场景：**

| 场景 | 处理方案 |
|------|----------|
| 条码污损无法扫描 | 提示"条码无法识别" → 点击"手动输入" → 输入 IMEI → 二次确认"条码不可读"原因 |
| 扫描到非目标设备 IMEI | 跨任务匹配时提示订单号 + 支持跳转；无任务匹配时阻止并告警 |
| 已出库设备重复扫描 | 提示出库时间 + 操作人 + "此设备已出库，不可重复核销" |
| 核销时网络中断 | 提交前二次确认不可跳过；提交时无网络 → 本地暂存核销结果（最近 20 条）→ 恢复网络自动提交 |
| B2B 批量核销中某台失败 | 失败设备单独标记"核销失败" + 原因；不影响同批次其他设备；可单独重试 |

**验收标准：**
- [ ] 扫描匹配的 IMEI 后展示完整核销确认卡
- [ ] IMEI 不匹配时展示正确告警信息并阻止出库
- [ ] 跨任务 IMEI 提示正确订单号并支持跳转

## WH-P1-01 批量出库

B2B 批量订单通常包含多台设备（可达数十台甚至上百台）。库管对每台设备逐台扫码核销后，一键批量确认出库并批量打印面单。批量出库流程展示实时进度，支持暂停/恢复和异常处理。

```
      │  📷 扫描 IMEI 条码                 │
      │                                  │
```

**验收标准：**

```
      └──────────────────────────────────────────┘
  → 提交后 → 盘点任务状态 = "待审核"
  → 管理员审核差异 → 逐项确认调整 → 库存数据修正
```

**盘点历史：**

| 字段 | 说明 |
|------|------|
| 盘点时间 | 盘点日期 + 持续时长 |
| 盘点范围 | 全仓 / 区域 / 品牌等 |
| 盘点人 | 执行盘点的库管姓名 |
| 盘点结果 | 账面数 / 实物数 / 差异数 |
| 状态 | 待审核 / 已调整 / 已关闭 |

**业务规则：**

| 规则项 | 说明 |
|--------|------|
| 盘点锁定 | 盘点开始后，盘点范围内的设备锁定不可出库；B2C 优先订单 SLA 不受盘点影响（可强制解锁出库） |
| 盘点周期 | 默认月度盘点（每月最后一天自动生成任务）；管理员可调整为季度盘点 |
| 手动盘点 | 库管可随时发起手动盘点（如怀疑库存异常） |
| 盘盈处理 | 实物有账面无的设备 → 补充入库记录或关联已有记录 → 管理员审核后入库 |
| 盘亏处理 | 账面有实物无的设备 → 管理员调查 → 确认为出库未核销/在途/丢失 → 分别处理 |
| 盘点超时 | 盘点任务 4 小时内未完成 → 自动暂停并告警；超 24 小时 → 自动关闭盘点锁定，恢复可出库 |
| 差异率 | 差异率 = |差异数| / 账面库存 × 100%；> 2% 标记"重大差异"，管理员重点关注 |

**验收标准：**
- [ ] 支持全仓/按区域/按品牌/按成色范围盘点
- [ ] 盘点进度实时展示（已盘点/账面应有）
- [ ] 盘点期间范围内设备锁定不可出库
- [ ] 差异报告自动生成（盘盈/盘亏分列 + 差异 IMEI 明细）
- [ ] 盘点历史列表展示完整，支持查看历史差异报告
- [ ] B2C 优先订单可在盘点期间强制解锁出库
- [ ] 盘点超 4 小时自动暂停告警，超 24 小时自动关闭
- [ ] 差异率 > 2% 标记"重大差异"

## UA-P0-04 账号安全与恢复
**优先级：** P0
**功能描述：**
提供密码修改、手机号更换、账号注销等账号安全功能，以及异常场景下的账号恢复机制。
**密码修改：**

```
App 设置 → "修改密码"
  → 输入旧密码
  → 输入新密码（8-20 位，至少含大写字母 + 数字）
  → 确认新密码
  → 点击"确认修改"
  → 服务端更新密码 → 所有设备 token 失效
  → 提示"密码已修改，请重新登录"
  → 返回登录页
```

**换绑手机号（需联系管理员）：**

```
店员 → 告知店老板 → 店老板联系 SA
SA 在内部业务应用（管理员视图）：
  → 找到该用户的账号
  → 点击"更换手机号"
  → 输入新手机号 → 系统向新手机号发送 OTP 验证
  → 验证通过 → 更新 phone 字段
  → 旧手机号自动解绑
  → 系统向新旧手机号同时发送通知 SMS
```

**安全设置：**

| 功能 | 说明 |
|------|------|
| 修改密码 | 需旧密码验证；修改后所有设备 token 失效 |
| 登录设备管理 | 查看当前已登录的设备列表（设备类型、登录时间、IP）；支持单设备远程登出 |
| 安全通知 | 新设备登录、密码修改、手机号更换等敏感操作向绑定手机号发送 SMS 通知 |

**异常场景处理：**

| 场景 | 处理方案 |
|------|----------|
| 忘记密码 | App 登录页"忘记密码"→ 输入手机号 → OTP 验证 → 设置新密码 → 所有设备重新登录 |
| 账号被盗 | 联系客服 → SA 后台强制踢出所有设备 → 重置密码 → 发送新临时密码到绑定手机号 |
| 手机号不能用（SIM卡丢失） | 联系客服线下验证身份 → SA 后台换绑新手机号 |
| 连续 5 次密码错误 | 锁定 15 分钟；锁定期间展示倒计时；不可使用 OTP 登录绕过 |
| 账号被禁用 | App 展示"账号已被停用"页面 + 联系管理员入口；5 分钟内当前会话自动登出 |

**账号注销：**

```
App 设置 → "注销账号"

      ├── 是否有进行中的订单（已售未发货 / B2B 待结算）？

      │     → 是 → 提示"您有待处理的设备，请联系管理员处理后再注销"
      ├── （仅店老板 ROLE-OWN）本门店是否有活跃店员？
      │     → 是 → 提示"您的门店下还有 X 名活跃店员，请先移除或转移后再注销"
      ├── （仅 DB ROLE-DB）是否有未完成的授信结算单？
      │     → 是 → 提示"您有未完成的结算单，请先完成后再注销"
      └── 全部通过 →
            → 展示注销确认页：
              ┌─────────────────────────────────────────┐
              │          确认注销账号                     │
              │                                         │
              │  注销后将立即发生：                        │
              │  · 账号冻结，无法登录                      │
              │  · 所有已登录设备被强制登出                 │
              │                                         │
              │  30 天冷静期内：                          │
              │  · 账号保持冻结状态                        │
              │  · 可联系客服申请取消注销                   │
              │  · 超期未取消 → 永久删除，不可恢复          │
              │                                         │
              │  永久删除后：                             │
              │  · 个人资料清除（姓名/手机号脱敏存档）       │
              │  · 操作日志保留（操作人标记为"已注销用户"）   │
              │  · 历史业务数据保留（订单/质检/结算，合规审计）│
              └─────────────────────────────────────────┘
            → 点击"确认注销"
            → 输入登录密码二次确认
            → OTP 验证（发送至绑定手机号）
            → 验证通过 →
                ├── 账号状态 → deleted_pending（冷静期）
                ├── user_role_assignment → disabled（所有角色实例）
                ├── 所有设备 token 失效 → 立即登出
                ├── 发送确认 SMS：
                │   "[Platform] 您的账号已申请注销，将于 30 天后永久删除。
                │    如需取消，请在 30 天内联系客服。"
                └── 系统定时任务：
                      ├── 每天检查 deleted_pending 超 30 天未取消的账号
                      ├── 永久删除 → 账号状态 → deleted
                      ├── 清除 personal_info：姓名、头像、密码哈希
                      ├── 保留 phone_hash（防重复注册）— 手机号脱敏后物理删除
                      ├── 保留审计数据：操作日志、登录日志、设备记录
                      └── 发送最终 SMS："[Platform] 您的账号已永久删除。感谢使用。"
```

**取消注销 — App 自助取消（冷静期内）：**

```
用户尝试登录 App
  → 服务端检测账号状态 = deleted_pending
  → 返回"注销冷静期"状态 + 剩余天数
  → App 展示冷静期页面：
      ┌─────────────────────────────────────────┐
      │          账号注销冷静期中                  │
      │                                         │
      │  您的账号已于 YYYY-MM-DD 申请注销          │
      │  将于 YYYY-MM-DD 永久删除（还剩 X 天）       │
      │                                         │
      │  冷静期内无法使用任何功能                   │
      │                                         │
      │       [ 取消注销 ]                        │
      │                                         │
      └─────────────────────────────────────────┘
  → 用户点击"取消注销"
  → 展示确认提示："取消后账号将恢复正常使用"
  → 确认 →
      → OTP 验证（发送至绑定手机号）
      → 验证通过 →
          ├── 账号状态 → active
          ├── user_role_assignment → active
          ├── 所有设备 token 保持有效（密码未变）
          ├── 发送 SMS 通知：
          │   "[Platform] 您的账号注销申请已取消，账号已恢复正常使用。
```

**取消注销 — SA 后台操作（备用通道）：**

```
SA 在内部业务应用（管理员视图）：
  → 找到该用户的账号（状态：deleted_pending）
  → 查看剩余冷静期天数 + 注销申请时间
  → 点击"取消注销"
  → 二次确认 + 填写操作原因（必填）

      ├── 同上恢复流程
      └── 操作日志记录 SA 操作人 + 原因
```

**注销异常场景：**

| 场景 | 处理方案 |
|------|----------|
| 冷静期内尝试登录 | 展示冷静期页面（剩余天数倒计时）+ 取消注销入口；不展示其他功能 |
| 冷静期内手机号尝试重新注册 | 该手机号不可注册（phone_hash 仍占用，冷静期内视为已有账号）；提示"该手机号已有关联账号" |
| 注销申请提交时网络中断 | 服务端以账号维度幂等：同一账号在 deleted_pending 状态下不可重复提交注销申请；请求超时后用户重试 → 服务端返回"注销申请已受理" |
| 30 天到期定时任务执行失败 | 每天凌晨扫描 deleted_pending 超 30 天的账号；单条失败不影响其他；连续 3 天扫描均失败 → 告警 SA 手动处理 |
| SA 强制提前永久删除 | 管理员可跳过冷静期直接执行删除（司法/安全/合规场景）；需二次确认 + 填写强制删除原因（必填）；操作记录审计日志 |
| 多角色用户注销 | 注销操作作用于账号级别：所有角色实例（OWN/WH/DB）的 user_role_assignment 同步 disabled；不可仅注销单个角色 |
| 已禁用/已锁定状态下申请注销 | 需先联系客服恢复账号为 active 状态，再发起注销申请；被禁用/锁定的账号不允许直接注销 |
| 冷静期内收到业务通知（如订单状态变更） | 不再向用户发送 SMS/推送通知（账号已冻结）；系统级通知保留在消息中心，恢复后可查看 |
| 店老板注销后其店员的第一联系人 | 注销前系统提示"您的店员将失去店老板联系人，请指定替代店老板或告知店员联系 SA"；不阻断注销但给出警告；注销后相关店员展示"店老板已离职，请联系 SA" |
| 注销后同一手机号重新注册 | 永久删除完成（30 天冷静期结束 + 定时任务执行）后，phone_hash 释放，该手机号可重新注册为新账号 |

| 注销前置条件 | 说明 |
|------|------|
| 进行中订单 | 已售未发货、B2B 待结算订单需先完成或取消 |
| 待处理设备 | 已质检未入库、待翻新判断、待审核等设备需先处理完毕 |
| 活跃店员（仅 OWN） | 店老板注销前需先移除或转移本门店所有活跃店员 |
| 未完成结算（仅 DB） | DB 角色下所有授信结算单需先完成 |
| 30 天冷静期 | 申请注销后进入 30 天冷静期，冷静期内可登录 App 自助取消注销 |
| 冷静期超期 | 30 天后系统自动执行永久删除，不可恢复 |
| 数据保留 | 个人资料清除（姓名/头像/密码哈希）；操作日志和历史业务数据保留用于合规审计；手机号脱敏存档防重复注册 |
| 冷静期内登录 | 仅展示冷静期页面 + 取消注销入口，不可使用任何业务功能 |

**验收标准：**
- [ ] 修改密码后所有设备立即登出
- [ ] 忘记密码流程：OTP 验证 → 设置新密码 → 重新登录
- [ ] 登录设备列表正确展示，支持远程登出单个设备
- [ ] 新设备登录向绑定手机号发送 SMS 通知
- [ ] 连续 5 次密码错误锁定 15 分钟，锁定期间 OTP 登录也禁用
- [ ] 账号被禁用后 App 展示明确提示
- [ ] 注销前置检查：进行中订单 / 待处理设备 / 活跃店员 / 未完成结算全部拦截成功
- [ ] 注销需密码 + OTP 双重验证
- [ ] 注销后所有设备立即登出，无法登录
- [ ] 注销确认 SMS 正确发送到绑定手机号
- [ ] 冷静期内登录展示冷静期页面（倒计时 + 取消注销入口），不可使用其他功能
- [ ] 冷静期内用户可通过 App 自助取消注销（OTP 验证），账号即时恢复正常
- [ ] SA 可在管理员视图取消注销（需填写操作原因），操作记录审计日志
- [ ] 30 天超期后系统自动执行永久删除，个人资料清除、业务数据保留
- [ ] 定时任务执行失败时告警 SA，支持手动处理
- [ ] SA 可强制提前永久删除（需二次确认 + 原因），跳过冷静期
- [ ] 已注销用户的手机号在永久删除后可重新注册
- [ ] 注销申请提交时网络中断 → 重试返回"注销申请已受理"，不产生重复记录
- [ ] 已禁用/已锁定账号不允许申请注销
- [ ] 多角色用户注销 → 所有角色实例同步 disabled

**门店关店——关联账号批量处理：**

```
SA 在内部业务应用将门店状态从 active → closed
  → 系统自动执行：
      1. 该门店所有 ROLE-CLK 和 ROLE-OWN 的 user_role_assignment → disabled
      2. 该门店所有平板设备 → 远程登出 + 锁定（展示"该门店已关闭"）
      3. 该门店所有待处理设备 → 标记为"门店关闭-待转移"
      4. 通知 DB
  → 该门店在库设备：
      ├── 已上架可售 → 正常售卖（通过仓库发货，不受门店关闭影响）
      └── 质检中/待审核 → 标记为异常，管理员介入处理
```
