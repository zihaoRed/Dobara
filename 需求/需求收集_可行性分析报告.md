## 需求 1：防止滥用 AI 定价 + 强制诊断费

### 1A. 转化率追踪与激励挂钩

| 维度 | 评估 |
|------|------|
| **当前是否已覆盖** | ❌ 未覆盖。当前流程有完整的会话数据（从到店到核销完成/拒收/拒绝报价），但没有按门店/经销商统计"检测→成交"转化率。 |
| **可增加？** | ✅ 可以，且建议增加。 |
| **建议优先级** | P1 |

**分析：**

当前系统已记录每一次换购会话的完整生命周期：
- `session_id` 绑定门店 ID + 店员 ID
- 会话有明确终态：已完成、已完成-拒收、用户拒绝报价
- 数据维度齐全：检测次数、成交次数、拒收次数

基于此，增加一个**门店转化率看板**是轻量级的数据统计功能：

```
转化率 = 当月成交会话数 / 当月总检测会话数
```

可以标记"转化率持续低于阈值（如 30%）"的门店，触发运营复查。激励挂钩（如高转化率门店享受更高佣金比例）属于 P2 运营策略配置化范畴。

**建议方案：**
- 在 CLOUD-P1-05（审核历史与效率统计）中扩展，增加门店转化率统计维度
- 在运营后台增设"转化率异常告警"标记
- 激励挂钩作为 P2 的佣金策略配置化一起做

### 1B. 强制诊断费（₹99-199）

| 维度 | 评估 |
|------|------|
| **当前是否已覆盖** | ❌ 未覆盖。当前流程在硬件审计前无任何收费环节。 |
| **可增加？** | ⚠️ 技术上可行，但 **不建议对 C 端消费者强制收取**。建议分渠道差异化处理。 |
| **建议优先级** | 视渠道而定 |

**分析：**

这个需求的核心矛盾在于**渠道差异**：

| 渠道 | 收取诊断费的合理性 | 风险 |
|------|:---:|------|
| **C 端消费者（直接到店/线上预约）** | 低 | 印度消费者对"先交钱再报价"接受度极低；竞品 Cashify 免费检测；会严重拉低到店转化率 |
| **B 端经销商（B2B 批量采购+换购）** | 高 | 经销商有动力滥用免费估价作为渠道比价工具；收诊断费可有效筛除非诚意询价 |
| **经销商高频低转化** | 高 | 正是需求 1A 要标记的那批人——对他们收诊断费是合理的反制手段 |

**建议方案：**

```
渠道差异化策略：
  ├── C 端消费者：不收取诊断费（保持竞争力）
  ├── B 端经销商（正常转化率）：不收取诊断费
  └── B 端经销商（转化率 < 阈值）：触发"诊断费模式"
       → 检测前收取 ₹99-199
       → 接受报价 → 从最终抵扣额中扣除
       → 拒绝报价 → 费用保留作为服务费
```

**技术实现要点（如果要做）：**
- 在质检前插入支付环节（Razorpay 小额支付）
- 需要处理"支付成功但质检未完成"的退款逻辑
- 诊断费状态机：待支付 → 已支付 → 已抵扣/已保留

**客户建议回复：**
> 诊断费这个方向我们认同，但建议不要对 C 端消费者一刀切。我们建议先上转化率追踪（1A），识别出低转化率的经销商后，**对这部分经销商单独启用诊断费模式**。这样做既保护了普通消费者的体验，又精准打击了滥用行为。我们可以先上转化率统计，运营一段时间拿到数据后，再决策诊断费的具体门槛。

## 需求 2：法律合规（DPDP Act、GST、电子垃圾、审计日志）

| 维度 | 评估 |
|------|------|
| **当前是否已覆盖** | ⚠️ 部分覆盖，有缺口。 |
| **可增加？** | ✅ 必须增加。 |
| **建议优先级** | P0（合规相关不可降级） |

**逐项分析：**

| 合规项 | 当前状态 | 缺口 | 建议 |
|------|:---:|------|------|
| **DPDP Act（数据保护）** | 部分覆盖 | 直接到店 H5 有隐私授权；但线上预约用户注册时虽同意隐私政策，质检环节的数据采集同意不够明确；数据删除机制仅在 P1 提及（用户注销后 30 天删除） | ① CLOUD-P0-11 增加"数据主体权利"模块（用户可请求数据导出/删除）；② 所有质检数据采集增加明确的 purpose specification 记录 |
| **GST 税务** | 部分覆盖 | 辅助需求文档中 GST 发票和税务报表为 P1；销售凭证生成已有但未明确 GST 税率计算 | ① 销售凭证生成时强制绑定 GST 税号；② 跨邦交易 IGST/CGST+SGST 计算（P1→提升至 P0 基础支持） |
| **电子垃圾法规 (E-waste)** | ❌ 未覆盖 | 印度 E-Waste (Management) Rules 要求回收商记录每台设备的最终去向；当前流程只到"已发货"，未跟踪设备最终处置 | ① 新增 E-Waste 追踪字段（设备是否最终拆解/翻新再售/出口）；② 运营后台增加 E-Waste 报告导出 |
| **数字审计日志** | 部分覆盖 | 状态机已有状态变更日志；核销、入库、出库均有操作记录；但缺乏统一的不可篡改审计日志存储方案 | ① 统一审计日志格式（操作人、时间、IP、操作类型、变更前后数据）；② P2 考虑区块链或 WORM 存储用于合规审计 |

**建议优先级排序：**

| 优先级 | 动作 |
|:---:|------|
| P0 | 审计日志统一格式 + DPDP 数据采集 purpose specification + 销售凭证 GST 绑定 |
| P1 | 用户数据导出/删除自助请求 + E-Waste 追踪字段 |
| P2 | E-Waste 报告 + 区块链审计存储 |

## 需求 4：先进先出（FIFO）原则

| 维度 | 评估 |
|------|------|
| **当前是否已覆盖** | ❌ 未覆盖。当前出库逻辑是"按订单匹配 IMEI"，不是"按入库时间优先级"。 |
| **可增加？** | ✅ 可以，且建议增加。 |
| **建议优先级** | P1 |

**分析：**

当前出库流程是**订单驱动**：用户下单锁定特定 IMEI → 该 IMEI 所在仓库按订单拣货。这个模式下，FIFO 并不直接适用——因为每个 IMEI 是唯一的，用户买的是"这一台设备"而不是"这个型号的任意一台"。

**FIFO 在 IMEI 级别的商城中的适用场景：**

| 场景 | FIFO 如何体现 |
|------|------|
| **B2C 个人购买** | 用户选择特定 IMEI，FIFO 不适用（用户主动选了这台） |
| **B2B 批量采购** | 门店按机型/成色筛选，不关心具体 IMEI → **这里可以应用 FIFO** |
| **商城列表排序** | 同机型+同成色+同价格的多台设备，默认排序可以把入库早的排在前面 → **间接实现 FIFO** |
| **仓库内部货位管理** | 物理货架按入库时间排列，拣货时优先取放得久的 → 仓库操作层面的 FIFO |

**建议方案：**
- B2B 批量采购时，同机型同成色的设备，默认优先分配入库时间最早的（WH-P0-02 出库任务逻辑修改）
- 商城列表排序增加"入库时间"权重（APP-P0-03 排序逻辑修改）：入库时间越早展示越靠前
- 仓库端 WH-P0-02 出库任务增加"入库日期"字段展示，方便库管按 FIFO 拣货
- 翻新手机备件的 FIFO 属于物理库存管理，建议 P2 在库存盘点功能（WH-P2-01）中增加批次管理

## 需求 5：IMEI 自动验证（黑名单/报失/分期/运营商锁）

| 维度 | 评估 |
|------|------|
| **当前是否已覆盖** | ✅ 已覆盖核心逻辑，有一处细节缺口。 |
| **可增加？** | ✅ 小范围补充。 |
| **建议优先级** | P0（缺口部分） |

**逐项对照：**

| 检查项 | 当前状态 | 位置 |
|------|:---:|------|
| 黑名单（报失/被盗） | ✅ 已覆盖 | CLOUD-P0-01 §3.3.2.0 准入检查："IMEI 黑名单"拦截项 |
| 运营商锁 | ⚠️ 隐含覆盖 | 黑名单库通常包含运营商锁设备，但未单独列出 |
| FRP/iCloud/激活锁 | ✅ 已覆盖 | CLOUD-P0-01 §3.3.2.0："iCloud/FRP 未退"拦截项 |
| 分期付款/EMI/贷款 | ❌ 未明确覆盖 | 当前准入检查未包含"设备仍在分期/EMI 中"的检查 |
| 进水/LCI | ✅ 已覆盖 | CLOUD-P0-01 §3.3.2.0："进水/受潮"拦截项 |

**需要补充的内容：**

**EMI/分期付款检查** — 印度市场大量手机通过 Bajaj Finance、HDB Financial 等 NBFC 分期购买。在贷款还清前，设备法律上不属于用户。回收这类设备有法律风险。

建议在准入检查中新增一行：

| 拦截项 | 判断依据 | 处理方式 |
|--------|----------|----------|
| 设备仍在分期/EMI 中 | 对接第三方 EMI 检查 API（如 Bajaj Finserv、HDB 等 NBFC 的 IMEI 查询接口），或要求用户提供贷款结清证明 | 拒绝回收，提示"设备仍在分期中，请结清贷款后再回收" |

> ⚠️ 注意：印度目前没有统一的 EMI 设备查询公共 API。实际落地可能需要：① 用户自行申报（法律免责声明）② P2 阶段对接主要 NBFC 逐一建立查询通道。

**建议：**
- P0：在准入检查中增加"分期/EMI 状态"拦截项，先以用户自行申报+免责声明方式实现
- P1：对接主要 NBFC（Bajaj、HDB）的 IMEI 查询 API
- P2：接入印度 DoT CEIR 系统的官方 IMEI 验证接口（当 API 可用时）

## 总结：优先级建议汇总

| 需求 | 建议 | 优先级 | 改动量 |
|------|------|:---:|:---:|
| 1A. 转化率追踪 | ✅ 增加 | P1 | 小——数据统计层 |
| 1B. 强制诊断费 | ⚠️ 分渠道差异化，不对 C 端收 | P1（仅对低转化 B 端） | 中——需支付+退款逻辑 |
| 2. 法律合规 | ✅ 必须补全缺口 | P0 | 中——多模块涉及 |
| 3. 实时流程追踪 | ✅ 逐步增加 | P1 | 中——物流 API + 前端追踪视图 |
| 4. FIFO 原则 | ✅ B2B 和排序中应用 | P1 | 小——排序逻辑+出库分配逻辑 |
| 5. IMEI 验证 | ✅ 核心已有，补 EMI 检查 | P0（EMI 缺口） | 小——准入检查加一行 |

**建议的迭代节奏：**

```
立即（P0）：
  ├── 审计日志统一格式 + DPDP purpose specification
  ├── 销售凭证 GST 税号绑定
  └── 准入检查增加 EMI/分期拦截（用户申报方式）

下一迭代（P1）：
  ├── 门店转化率统计 + 异常标记
  ├── DB→仓库物流追踪（接入 Shiprocket）
  ├── B2B 采购 + 商城排序应用 FIFO
  ├── NBFC EMI 查询 API 对接
  └── 低转化率经销商诊断费模式

远期（P2）：
  ├── E-Waste 报告 + 区块链审计
  ├── 退货 + 保修索赔流程
  └── 激励/佣金策略配置化
```
